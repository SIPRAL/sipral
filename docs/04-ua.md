# sipral-ua: the user agent

Policy over the primitives in `sipral-core`. Still sans-I/O.

## Accounts and registration

An account is credentials, a registrar (or none, for a trunk), a proxy and
transport preferences. Several accounts coexist in one stack without sharing
anything.

Registration:

- `REGISTER` with `Expires`, refreshed at a fraction of the granted expiry.
  The fraction is a design choice, not a spec value: 0.85 by default, and never
  later than 30 s before expiry, so one lost refresh and one retransmission
  round still fit before the registrar drops the binding. Never sooner than
  halfway either, so a registrar handing out very short bindings does not turn
  the client into a metronome;
- the registrar's granted expiry wins over the requested one, always. It is
  read from the `expires` parameter of the `Contact` the registrar echoed back
  for us, found by §19.1.4 equivalence, then from `Expires`, then from what was
  asked for. A contact list that does not name us is *not* read as a removal:
  registrars rewrite addresses behind a NAT, and only a stated zero means the
  binding is gone;
- one `Call-ID` for every registration of a boot cycle (§10.2.4), with the
  sequence number growing across refreshes;
- `Contact` carries a stable `+sip.instance` (RFC 5626 §4.1) when the
  application supplies one, so a re-registration from a different address
  replaces rather than duplicates. The URN is the application's to generate and
  to store, because it has to survive a power cycle. The `reg-id` that goes
  with it in an Outbound registration is deliberately not sent: RFC 5626 §4.2
  pairs it with the `outbound` option tag and per-flow registration, which are
  not implemented; the §4.4.1 CRLF keepalive and dead-flow detection are;
- a 423 raises the interval to the `Min-Expires` demanded and tries once more
  (§10.2.8). A second 423 is the registrar contradicting itself, and stops;
- a challenge is answered from the account without asking the application, and
  once it has been, every REGISTER after it carries the answer on the way out
  rather than waiting to be refused again (§22.2). The first registration of a
  boot costs two round trips and every refresh after it costs one, which is
  half of what an hourly refresh used to pay for the life of the process. The
  same challenge coming back after it was answered — ahead of the refusal or
  after it — is §22.1's way of saying the password is wrong, and it stops there:
  repeating it is how an account gets locked out. A nonce the registrar has
  aged out comes back marked `stale`, which is a different thing and gets one
  more attempt with the new one. A registrar that draws a fresh nonce for
  every refusal and never says `stale` defeats that guard, so there is a
  second one underneath it, and it is the endpoint's rather than this layer's:
  one request is answered at most three times, whatever nonce comes back. That
  allowance covers every path that answers a challenge, not only registration
  — a call, an in-dialog request, a re-INVITE or UPDATE, a SUBSCRIBE — and the
  refusal arrives as `RegistrationFailed`, `CallEnded`, `SessionChangeFailed`
  or `SubscriptionEnded` on each;
- the password answers the account's own server and nobody else (§22.1: "each
  such protection domain has its own set of usernames and passwords"; RFC 7616
  §5.10 and §5.11: every answer is material for an offline search of the
  password by whoever chose the nonce). A challenge to a request that went
  anywhere but the account's registrar — or its outbound proxy, for an account
  that does not register — is not answered (the server's address is what is
  compared, not its port, since a PBX that takes TCP on another port than UDP
  is the same server over the stream §18.1.1 asks for, and in its canonical
  form, an IPv4 address and its IPv4-mapped IPv6 form being one server): the
  far end of a call reached directly, or one inside a dialog that has its own
  address, challenging a re-INVITE or a BYE, gets nothing. Neither does a
  challenge from the server for a realm that is not the account's: the realms
  `Account::realms` names (`sipral_account_config_t::realms` in C, one per
  line), and those alone, REGISTERs included; or, with none named, the ones
  the server first challenged the account with, together with every realm
  the account's own REGISTER is ever challenged for — so a proxy passing on a
  far end's own 401 under the far end's realm gets nothing either. A
  REGISTER's challenge is always the account's, since nobody passes a
  REGISTER on to a far end of their choosing: a registrar that moves to
  another realm is followed on the next refresh or registration, where the
  first realm taken used to be kept for the life of the account and every
  registration after the move failed. What the REGISTERs never meet is not
  learned: an SBC or outbound proxy at the registrar's address that
  challenges calls with a realm of its own while the registrar challenges
  REGISTERs with another needs both named, or its calls are declined. Every path that answers a
  challenge is held to this, and a challenge declined is closed at the
  endpoint too, so that §22.2's answer ahead of a challenge does not hand the
  same party one on the next request. The application hears
  `UaEvent::ChallengeDeclined` with the address, the realms and why
  (`ChallengeRefusal`) — `SIPRAL_EVENT_KIND_CHALLENGE_DECLINED` over the C
  ABI, with `payload.challenge` — and the decision is recorded as
  `auth.challenge.declined`; then the refusal settles as any unanswered
  challenge does. What this cannot tell apart is a far end behind the
  account's own proxy that names the account's realm: the address is the
  proxy's and the realm is right, and only the proxy can refuse to pass such a
  challenge on;
- de-registration with `Expires: 0` when the application calls
  `UserAgent::unregister(account, now)` before exiting (nothing is sent on
  drop), for this device's binding only. A `Contact: *` would remove every
  binding the address of record has, including the desk phone somebody else
  is holding. A de-registration that times out, loses its transport or is
  answered 5xx is retried on the back-off below as a de-registration, the
  account staying `Unregistered` meanwhile: a retry never asks for the
  binding back after the application asked the account to leave. One that
  has to wait before it goes — for the lookup of a registrar named by a URI,
  or for the account's own connection — reads `Unregistered` from the call
  too, supersedes a REGISTER still in flight, and is what goes when the wait
  ends;
- backoff on failure that distinguishes *rejected* (403, 404, and the rest of
  the 4xx: stop and report) from *unreachable* (timeout, dead transport, 5xx:
  retry). The schedule is RFC 5626 §4.5's — `W = min(1800 s, 30 s · 2ⁿ)`, with
  the wait drawn uniformly between half of W and W — because a thousand phones
  that lost the same server must not come back in the same second. A
  `Retry-After` can push the wait out, never pull it in;
- a flow that dies under a live binding counts as unreachable too. RFC 5626
  §4.4.1 has the core call it dead when a keep-alive goes ten seconds
  unanswered, and §4.4 sends the UA to §4.2 for a new flow; opening one is the
  application's, and what happens here is the rest — the binding is not live,
  and the REGISTER that says so again goes on the same back-off. A binding with
  a REGISTER already in flight is left to the transaction that is about to fail
  with the transport, because counting one outage twice doubles the wait;
- a 3xx is reported rather than chased. Following one needs an address, and
  resolving a name is the caller's;
- `UserAgent::retarget` moves an account to a different registrar address — a
  second SRV target, a failover a proxy pushed, an operator's migration —
  without touching anything the binding stands on: the `Call-ID`, the growing
  sequence number and the credentials are exactly what they were. Only where
  the *next* REGISTER is addressed changes. A REGISTER already in flight, or
  one a back-off has scheduled, is superseded rather than raced: the account's
  next attempt goes to the new address at once, on the same rule that already
  lets a second call to `register` supersede one still running, rather than
  waiting out the attempt failing on its own or the next scheduled refresh.
  Retargeting to the address an account is already on does nothing. Contrast
  `UserAgent::rebind` (`docs/16-lifecycle.md`): that one is *this end's own*
  address moving, carries a new `Contact` because of it, and answers the
  lifecycle ladder; a registrar moving under an otherwise healthy account is
  neither.

An account and a registration, exactly as `crates/sipral/examples/register-and-call.rs`
builds and drives them — that file is a compiled example
(`cargo run --example register-and-call -- --user U --pass P --domain D --target sip:...`),
so this is read off the source rather than typed fresh:

```rust
let account = endpoint.add_account(
    Account::new(aor, registrar, contact, endpoint.transport, remote)
        .credentials(Credentials::new(&args.user, &args.pass)),
);
endpoint.agent.register(account, now)?;
```

State is reported as events: `Registering`,
`Registered { expires, refresh_in, response, info }`, `Refreshing`,
`RegistrationFailed { reason, status, retry_in, response }`, `Unregistered`.
Both answers ride whole, the grant as much as the refusal, because a reason
phrase, a `Retry-After`, the `Contact` of a redirect or the `Contact` set a
registrar holds for the address of record says more than a status code or a
lifetime can. Through the C ABI the same 2xx is the event's `message`.

### A server by its name, a flow kept open, an address a peer can reach

**The server can be named rather than addressed.** `Account::located` takes
the registrar as a URI whose host RFC 3263 finds, `Account::unregistered_located`
does the same for a trunk's outbound proxy, and `Account::locate(server)`
points any account's requests at a server so named. The procedure is this
tree's (`sipral_core::endpoint::Locator`): NAPTR when the account asks for
it, SRV for the account's transport (`_sip._udp`, `_sip._tcp`, `_sips._tcp`),
then A or AAAA; a URI with a port skips SRV and a numeric host asks nothing.
The lookups are the application's resolver's, handed out one at a time as
`UaEvent::LookupWanted` and answered with `UserAgent::looked_up`, a resolver
that cannot ask for NAPTR or SRV answering "nothing" and the host's own
addresses then used. Every address found is kept in §4.3's order: a REGISTER
that times out, loses its transport or is answered 503 moves to the next at
once, and the name is asked again when none is left, when the answer's
shortest time-to-live runs out, or when the recovery ladder wants an address
(`docs/16-lifecycle.md`), so a PBX that changes address is followed without a
restart. Until the first answer, a call, MESSAGE, SUBSCRIBE or PUBLISH that
names no destination of its own is `UaError::NotLocated`.

**Every request fails over, not only the REGISTER.** An INVITE, MESSAGE,
SUBSCRIBE or PUBLISH outside a dialog that went to the address a located
account's name gave, and that times out, loses its transport or is answered
503, goes again at once to the next address of the same answer — §4.3's "new
request, which is identical to the previous, but has a different value of the
Via branch ID". The endpoint keeps every request outside a dialog that failed
one of those three ways (`Endpoint::unreached`, capped at 32) and sends it
elsewhere on request (`Endpoint::send_elsewhere`), dropping credentials meant
for the server that failed; the agent does that before any handler sees the
failure, moves whatever held the request — the call, the message, the
subscription, the publication — onto the new transaction, and points the
account at the new address. The application hears only a failure with no
address left to try. A request sent to a destination of its own, or one inside
a dialog, is not moved: a dialog fails over by its own route set
(`sipral_core::endpoint`'s resolve module).

**An account can have a connection of its own.** One agent holds an account
on the stack's UDP transport with one PBX and another on TCP or TLS with a
second: `Account::on_stream(protocol)` names the protocol, and the agent asks
the application for a connection to the account's server with
`Event::TransportWanted` — the event §18.1.1 raises for a request that
outgrew a datagram, here with no request behind it, `request_bytes` and
`limit_bytes` zero — and adopts whichever transport of that protocol the
application binds to that address, under any number; one bound before the
account was added is used as it is. Until then the account names no transport:
its REGISTER waits, `oversize::STREAM_WAIT` (ten seconds) after the question
it fails as unreachable and its retry asks again, and a call it places is
refused for an unknown transport with nothing sent. An account that never
registers asks when it is added; any account asks again at once when its
connection closes or fails, a registered one by registering again, since
nothing reaches it until it does (RFC 5626 §4.4.1). A located server is looked up for the connection's protocol
(`_sips._tcp` for TLS) before any connection exists. Each call keeps the flow
its INVITE went over for every request inside it, so two lines on two
transports never cross.

**An incoming request finds its account by its flow too.** The Request-URI
against each account's `Contact` and the `To` against its address of record
still name the line; among the lines either names, the one whose requests use
the transport the request arrived on wins, and then the one whose server it
came from — two accounts with the same user and the same contact on two
servers, or on UDP and on TLS, each get their own calls. With neither URI
matching, an account on the arrival flow whose contact has the Request-URI's
user is the line: a server that rewrote the host of the contact it was given
still names the user it registered. No match at all is still not a refusal.

**A flow can be kept open at an interval of its own.** `Account::keepalive`
(one to 120 seconds) keeps the account's flow to its registrar, or a trunk's
to its outbound proxy, open whatever STUN found: a double CRLF on UDP and the
endpoint's ping on a stream, sent between 80 and 100 % of the interval as RFC
5626 §4.4 asks (`docs/06-nat.md`). Unset, an account is kept open only when
STUN showed it behind a NAT.

**A PBX's own certificate can be pinned.** `Account::tls_pin` takes the
SHA-256 fingerprint of the one certificate the account trusts, and the
application's certificate verifier asks `CertificatePin::check` about the
leaf the server presented (`docs/22-tls.md`, "A PBX's own certificate,
pinned").

**A loopback address is never advertised to a peer elsewhere.** A REGISTER's
`Contact`, or a call's `Contact` and session description, that would hand a
loopback address to a peer that is not itself on loopback — or the
unspecified address in a `Contact` — is refused with
`UaError::UnreachableAddress` before anything is sent, and a refresh the agent
sends on its own fails as `RegistrationFailure::UnreachableContact`
(`docs/06-nat.md`, "The address this end advertises").

### What the registrar says beside the binding

A 2xx to a REGISTER can carry three more things. `Registered::info` holds what
could be read of them, and `UserAgent::registrar_info` reads the same back:

- **Service-Route** (RFC 3608). Replaced by every 2xx and cleared by one
  without it (§6.1); dropped when a refresh is refused for good, by a final
  non-2xx including a 5xx, but kept through a timeout, which is no answer at
  all, and through a 423 whose `Min-Expires` the stack obeys, since that refresh
  is sent again at once and the binding has not been denied. It is
  preloaded, in the registrar's order, as the `Route` of the requests the
  account starts towards the address it registers with — an INVITE, a
  SUBSCRIBE — and **not** on the REGISTER refresh: §3 hands it out to reach the
  services of the system registered with, and a refresh sent along a stale
  route could never be the thing that replaces it. A request the application
  sends elsewhere with `to_address` takes none of it, and requests inside a
  dialog follow the dialog's own route set as they always did. Only loose
  routes are taken, as §5 requires; nothing here rewrites a Request-URI for a
  strict one.
- **GRUU** (RFC 5627). A REGISTER from an account with an instance identifier
  carries `Supported: gruu` (§4.1), folded into any `Supported` the application
  added. The `pub-gruu` and `temp-gruu` are read from the `Contact` whose
  `+sip.instance` is this device's — never from whichever contact comes first,
  which lists another device as often as not. The instance is compared as a
  URN, the way RFC 5626 §4.1 says, and not byte for byte: `urn:` and the
  namespace without regard to case, a `uuid`'s hexadecimal the same, and the
  rest of any other URN exactly. They become the `Contact` of the INVITE, of
  the 18x and 2xx that answer one, of the SUBSCRIBE and its refreshes, and —
  since a call must not repeat one either (below) — of every other request and
  response a call builds inside its dialog too: the public GRUU while
  registered and issued, a temporary one when the request carries a `Privacy`
  other than `none` (§3.3), and the configured contact when an anonymous
  request has no temporary GRUU, because the public one names the address of
  record it is hiding. The GRUU goes out bare, with no `+sip.instance`, as §9
  writes it and as §10.3 needs for a temporary one. `Supported: gruu` goes on
  every INVITE this end sends, a re-INVITE included, on the 18x and 2xx it
  sends to an INVITE or a re-INVITE, and on the SUBSCRIBE and its refreshes,
  the same way it goes on the REGISTER, and
  `Require: gruu` on an incoming request is honoured rather than answered 420
  once the account has asked for GRUUs of its own (§4.4 is written from a UA's
  own use of them, but understanding the mechanism well enough to ask for one
  is understanding it well enough to be asked back).
  A refused refresh leaves the GRUUs alone (§4.2); a binding given up or
  granted for zero seconds takes them with it (§5.3), and so does a restored
  snapshot, a suspend, or a lost network: a binding the stack has stopped
  believing in lends nothing to a call until a 2xx proves it again, because
  the lapse that would otherwise stop them is read from a clock that did not
  run while the machine slept. The REGISTER's own `Contact` stays the device's. Self-made GRUUs
  and the RFC 5628 extension to the registration event package are not
  implemented.
- **P-Associated-URI** (RFC 7315, which obsoletes RFC 3455). Reported and not
  acted on: §4.1 says a UAC must not assume the associated identities are
  registered.

None of it outlives the binding it came with. It is read at the moment of use
and answers nothing once that binding has lapsed, which is the point RFC 5627
§4.4 and RFC 3608 §6.1 both turn on. Every value comes from a peer and goes
back out in this account's own requests, so every one is parsed with the core's
parsers and bounded — eight route entries, thirty-two associated identities,
512 bytes a value, no control bytes, folds joined, and no byte in a route hop
or a GRUU that RFC 3261 §25.1 does not write a URI with, so a `>` inside one
cannot end the header it is written back into — and a field that does not
survive that is left out whole, never in part, and written into the REGISTER's
diagnostic record as `registration.service_route.ignored`,
`registration.gruu.ignored` or `registration.associated_uri.ignored`. The
binding still stands: what a registrar garbled beside a grant does not undo the
grant.

A call's `Contact` is read fresh every time, never kept from when the dialog
opened. §4.4 forbids naming a GRUU once the registration that issued it has
lapsed or been removed, which a re-INVITE, a session-timer `UPDATE`, a REFER or
a NOTIFY sent long into a call would otherwise do by repeating the `Contact`
the INVITE opened with — the same staleness a subscription's refresh already
read around. Every one of those reads the account's registration state at the
moment it is built instead. A `Contact` that changes in a re-INVITE (RFC 3261
§12.2, the base target refresh) or an `UPDATE` (RFC 3311 §5.1, also one) moves
the peer's remote target; a REFER is answered like a BYE and does not, and a
NOTIFY does too (RFC 6665 §3.2 makes it a target refresh request as well) — in
neither case is repeating the value wrong, since RFC 3261 §12.2 lets any
in-dialog request carry a `Contact` whether or not it is one that acts on it.
A call whose account is removed while it is up has no registration left to
read, and names the plain contact the account had when the call began rather
than an empty `Contact`.

Two more states exist for a machine that is not always awake, and neither of
them is a claim about the registrar:

- **`Unverified`** — a binding a registrar really granted, over a transport
  that has since been suspended or lost, which nothing has proved since. Not
  `Registered`, because it has stopped being evidence; not `Failed`, because
  nothing refused it. It exists because **a monotonic clock cannot tell you
  that you slept**: it does not advance during suspend, so a stack that slept
  eight hours wakes believing eight milliseconds passed, with every deadline
  still ahead of it and every binding still valid, and nothing it can measure
  says otherwise. `docs/16-lifecycle.md` is the whole of it.
- **`Restored`** — a binding read back from a snapshot rather than granted in
  this process, which has not been proved either. `docs/15-mobile.md` covers
  the snapshot and its version rule.

An account can also have **no registrar at all**:
`Account::unregistered(aor, contact, transport, outbound_proxy)`, for a trunk
that knows this end by the address its requests come from. Every request it
places goes to the outbound proxy unless it names a destination of its own, and
a challenge from the proxy is answered from the account's credentials as it is
anywhere else. Its state is **`NotRegistering`** from the moment it is added,
and nothing moves it. It is not `Idle`, which is one `register` away from a
binding: `register` and `unregister` answer `UaError::NoRegistrar` and build
nothing. Everything that exists to protect a binding has nothing to do for it,
and each part says so rather than trying:

- no refresh and no back-off is ever scheduled, because both start from a
  REGISTER;
- a wake, a move and a lost resolver neither doubt it nor re-register it
  (`docs/16-lifecycle.md`);
- a push has no binding to refresh: `refresh_binding` answers `NoRegistrar`
  and remembers nothing as owed, and `announce` still records the call it
  announces;
- no snapshot is written for it, and one offered to it is refused with
  `SnapshotError::NotRegistering`;
- `time_to_ready` has no moment to measure and stays `None`.

Its subscriptions were never tied to a binding, and behave as any account's do.

A refresh that could not reach a transport is *not* a registrar refusing. It
backs off and tries again, the same as a failure on the wire, because the shape
this happens in is the ordinary one on a machine that slept: the deadline falls
due before the socket has been rebuilt. Treating it as permanent killed the
account for the life of the process, and did so silently.

### Suspend, resume, and a network that changed

`UserAgent` takes `suspending`, `resumed`, `network_changed(from, to)`,
`interface_lost` and `name_resolution_lost` from the application, because the
stack cannot detect any of them. Each has a written recovery ladder, and
`suspending` deliberately sends nothing at all — a graceful de-registration
cannot be observed to have left, and if it does leave, a de-registered device
cannot be woken by a push. The states, the ladders, the guarantee that no
failure of a network operation terminates the process, and what that guarantee
does not cover are all in `docs/16-lifecycle.md`, and so is what happens to a
call in progress when the address changes: `UaEvent::CallAddressWanted` names
it, and the facade's `MediaEngine::readdress` offers it at the new one.

`idle()` answers what is still scheduled and what it costs, which is what makes
"cheap when backgrounded" measurable rather than asserted.

Known trap: one widely deployed PBX ships its SIP channel driver with
`max_contacts=0`, which refuses every registration. It is a server
misconfiguration, and it will be blamed on the client, so
`RegistrationFailure::hint` names it — as a note about what usually causes a
blanket refusal, not as a diagnosis, because nothing on the wire proves it.

### Voice quality reports

`Account::quality_report_uri` is opt in, per account: unset, a call on that
account never sends one. Set, `UserAgent::send_quality_report` — called by the
facade once a call has ended, with the RFC 3611 figures the media layer
measured — publishes an RFC 6035 `VQSessionReport: CallTerm` to it over a
PUBLISH (RFC 3903), `Event: vq-rtcpxr`. `quality_report::QualityReportMetrics`
is plain scalars, not a dependency on anything that touches RTP: this crate is
signalling, and the body's `CallID`/`LocalID`/`RemoteID`/`OrigID` lines come
from the call's own `CallIdentity` and `Direction` instead, which decide which
of `CallIdentity`'s two URIs is this end's own. The PUBLISH is fire and
forget — `Expires: 0` closes its own published state immediately, since the
report describes a call already over and nothing here refreshes it — and a
call this method does not know, or whose account named no collector, is a
silent `Ok(false)` rather than something the caller has to check for first.
`docs/05-media.md`'s RTCP section has the rest: where the figures come from
and how the E-model rates them.

## Calls

State: `Calling → Ringing? → EarlyMedia? → Confirmed → Terminating →
Terminated`, with `Incoming → Ringing? → Confirmed` on the other side.

Placing one, from `crates/sipral/examples/call.rs` — the whole of what the
zero-configuration example needs beyond opening a socket and picking an
account, since [`MediaEngine::place`](../crates/sipral/src/engine.rs) writes
the offer and opens the session together:

```rust
let outgoing = OutgoingCall::new(Uri::parse_str(TARGET)?).to_address(endpoint.transport, remote);
let call = udp_endpoint::place(&mut endpoint, account, outgoing, now)?;
```

`udp_endpoint` is the examples' own helper
(`crates/sipral/examples/common/udp_endpoint.rs`), not part of the crate's
API.

and the two events that matter answering back, from the same file's own event
loop:

```rust
Event::Signalling(UaEvent::CallConfirmed { call: this, .. }) if this == call => {
    println!("connected");
    confirmed_at = Some(now);
}
Event::Signalling(UaEvent::CallEnded { call: this, reason, .. }) if this == call => {
    println!("call ended: {reason}");
    ended = true;
}
```

`Consulting` sits beside `Confirmed` and means the same thing to the protocol:
a confirmed dialog, held, renegotiated and hung up like any other. What it adds
is why the call exists — it is the second leg an attended transfer needs, placed
with `consult` from the call that is going to be handed over. Without a name for
it the application is the only thing that remembers which of two live calls is
the consultation, in the middle of a three-party operation where getting it the
wrong way round hands the wrong person to the wrong person. It survives
everything the target does to the session — a hold, a codec change, a session
refresh — because none of those says anything about what the call is for. When
the call it was placed for ends first, there is nobody left to hand over and it
becomes an ordinary `Confirmed` call.

A `CallHandle` names one dialog rather than one attempt, because one INVITE can
open several. Placing a call mints one, the first early dialog adopts it, and
each further branch of a fork arrives as a sibling under `CallForked`. What
happens to the siblings is `ForkPolicy`, and the default is what a telephone
does: keep the first that answers, acknowledge every other 2xx — §13.2.2.4 does
not make that conditional on wanting the call — and hang them up. `KeepAll` is
for a bridge or a recorder that wants both legs.

The first that answers is whichever branch's 2xx arrives first, the call placed
or a sibling: a proxy that rings a desk phone and a mobile in parallel forwards
the mobile's 2xx and cancels the desk (§16.7), so a stack that kept only the
call placed would hang up the one phone that answered and wait on one that
never will. The branch kept is reported up with `CallConfirmed`, and then every
branch still ringing ends with `CallEnded` and `ForkLost` — the application
reads which one won off those two, and carries on with the handle that was
confirmed. A 2xx that arrives on any other branch afterwards, or on a branch
never heard of before, is acknowledged and hung up without an event. A sibling
kept is the call: it answers to the same `Call-ID` and parties, its session is
the one its own 2xx described, and a transfer it was placed for or the
consultation it is moves onto it before the branch it came from ends. A 2xx
that crosses the CANCEL of a call the user put down is hung up whichever branch
it came from, and nothing of it is kept. Until the INVITE's answer window
closes (64*T1 after its first 2xx), a 2xx from another branch is acknowledged
and hung up even when the call it would have joined — the one kept, or the one
the user put down — is already over. That holds under `KeepAll` too: while a
leg of the fork is still up, a late branch is minted beside it as one more
sibling, and once every call the INVITE made has ended a 2xx is acknowledged
and hung up rather than dropped. The same goes for a 2xx that follows a
refusal — a proxy forwards every 2xx even after the 486 or 603 it already
sent (RFC 3261 §16.7), and the INVITE's transaction passes it up until timer
D ends it (RFC 6026 §8.4) — so a call reported `Refused` never leaves a
dialog standing at a far end that answered late.

Outgoing: INVITE with an offer, or without one where the offer comes back in
the 2xx. Provisional responses become events with the response whole, so early
media plays before the call is answered. The ACK for a 2xx is sent by the stack
rather than offered to the application: the core leaves it open because it may
have to carry an answer, and a 2xx nobody acknowledges is retransmitted for
64·T1 and then hung up at the far end. The one case that waits is the call
placed without an offer, where the answer has nowhere else to travel and only
the application has one.

Incoming: `100 Trying` immediately, then application policy decides between
`180 Ringing`, `183 Session Progress` with early media, `200 OK`, or a
rejection. An INVITE is matched to the account it was addressed to — by the
Request-URI against the contact, then the `To` against the address of record —
and one that matches neither is still reported, because a misrouted call that
vanishes silently is worse than one that can be seen.

Hanging up means three different things and takes one call. Before the INVITE
is answered it is a CANCEL, which §9.1 will not let go before the first
provisional response and which the core holds until one arrives; after it is a
BYE; on a call that came in and has not been answered it is a refusal. An
application that has to know which is an application that will get it wrong
during the second it matters.

A 2xx this end sent and nobody acknowledged ends the call with a BYE.
§13.3.1.4 asks for it and §14.2 repeats it for a re-INVITE, and there is
nothing else that would: the far end has stopped answering, and a dialog left
standing keeps a line busy for as long as the process runs. The call is
reported as `Unreachable`, which is what it is.

An application's own header fields reach a call three ways, and are checked the
same way on all three before anything is built: `OutgoingCall::header` on the
INVITE, `Account::header` on every REGISTER, and
`UserAgent::respond_with_headers` for what the call sends afterwards at the
application's request. That is the 180 or 183 from `ring`, the 200 from `answer`
(one RFC 3262 §5 held back included), the refusal from `reject`, the refusal or
the BYE `hangup` turns into, and the re-INVITE or UPDATE of `hold`, `resume` and
`reoffer`, a retry after a 491 included. Those fields are kept until they are
replaced, whole, rather than spent on the first message: an application that
labels a call labels all of it. A CANCEL never carries them, because it is hop by
hop (§16.10) and nothing written on it reaches the far end. Neither does anything
this layer sends by itself — a session refresh, the BYE for a 2xx nobody
acknowledged, for a fork that lost, or for a hangup whose CANCEL lost the race to
the 200 — because a field the application wrote is the application speaking, on a
message it asked for; nor the answer to a change the far end offered, which
belongs to the far end's request.

A field is refused, as `UaError::Header`, when its name is not a token, when its
value holds a control byte other than a tab, or when this stack writes that field
itself on those messages. A second line of one of those is not a second opinion
the far end weighs: it is a malformed message, or one that goes somewhere, ends
somewhere or promises something the stack did not mean. `HeadersFor::check` is
where the list is kept, and the core refuses its own part of it from
`OutgoingRequest::header` and its two siblings as well (`ENDPOINT_FIELDS`,
`BuildError::OwnedField`), so no path writes one twice.

| Field | Refused on | Why the stack owns it |
|---|---|---|
| `Via` | everything | RFC 3261 §8.1.1.7, §18.2.2: the branch keys the transaction, and the sent-by is where the response comes back to |
| `From`, `To` | everything | §8.1.1.2, §8.1.1.3: the tags name the dialog, and each field appears once |
| `Call-ID` | everything | §8.1.1.4: the dialog's name, once |
| `CSeq` | everything | §8.1.1.5, §12.2.1.1: the number a transaction and a dialog are ordered by |
| `Max-Forwards` | everything | §8.1.1.6: the hop count a loop is caught by |
| `Contact` | everything | §8.1.1.8, §12.1.1: the remote target the far end sends the dialog to |
| `Route` | everything | §8.1.2, §12.2.1.1: the route set; a hop written by hand detours the request through a proxy the application named |
| `Record-Route` | everything | §12.1.1: copied into a response that opens a dialog, and the far end reads its route set off it |
| `Content-Type` | everything | §7.4.1, §20.15: what the body is, written with the body |
| `Content-Length` | everything | §18.3, §20.14: where the message ends on a stream; a second one starts a second message |
| `Allow` | a call | §20.5, RFC 3311 §4: the methods this end answers |
| `Supported` | a call | §20.37, RFC 3262 §4, RFC 4028 §7.1: the extensions this end supports, which the far end acts on |
| `Require` | a call | §20.32, RFC 3262 §3, RFC 4028 §9: an extension the far end has to follow |
| `RSeq` | a call | RFC 3262 §7.1: the number of a reliable provisional, which the PRACK acknowledges by |
| `Session-Expires`, `Min-SE` | a call | RFC 4028 §4, §5: the session timer this end negotiates and runs |
| `Authorization`, `Proxy-Authorization` | a call, a REGISTER | §22.2, §22.3: the answer to a challenge, from the account's credentials, with a nonce count only one writer may keep |
| `Expires` | a REGISTER | §10.2.1, §20.19: the binding's lifetime, which the refresh schedule is computed from |

Left open on purpose: `Expires` on an INVITE, which limits how long the
invitation stands (§13.2.1); `Supported` on a REGISTER, which a registration that
wants a GRUU has to write (RFC 5627 §4.1); and `Replaces` and `Referred-By`, which
this layer writes only on the INVITE an accepted transfer places, while an
application writing `Replaces` on a call it places itself is taking over a dialog
it learned about some other way (RFC 3891 §1). On that one INVITE both are the
REFER's, and `accept_transfer` refuses either among the application's fields:
RFC 3891 §3 has an INVITE with more than one `Replaces` refused with a 400, and
on a blind transfer one of the application's own would take over a dialog the
REFER never named. A compact name is the field it
abbreviates, so `m` is refused where `Contact` is. The C ABI adds `User-Agent`
when the stack was configured with one (`docs/08-ffi.md`).

There is no auto-answer setting, and there should not be: it is the application
answering the `IncomingCall` event immediately, which is one line, and a 200
has to carry a session description that only the application has. The headless
profile does exactly that. Whether the caller asked for it is read, not acted
on: see the next section.

## Who is calling, how to answer, why it ended, and where it went

`From` is what a caller wrote about itself. Everything else a phone shows about
an incoming call comes from other fields, and this layer reads them once, as the
INVITE arrives, into `UaEvent::IncomingCall::identity` — the same
`CallIdentity` that `call_identity(call)` answers for the rest of the call:

| Field | Read into | Where from |
|---|---|---|
| `P-Asserted-Identity` | `caller.asserted` | RFC 3325 §9.1: one or two parties, a SIP URI and a `tel:` one |
| `Remote-Party-ID` | `caller.remote_party` | draft-ietf-sip-privacy-04 §9, which RFC 3325 replaced and switches still send |
| `verstat` on the asserted URI, or on `From` | `caller.verstat` | 3GPP TS 24.229 §7.2A.20: the number checked, and what the check said |
| `Privacy` | `caller.privacy` | RFC 3323 §4.2, and RFC 3325 §9.3's `id` |
| `Diversion` | `caller.diversions`, most recent first | RFC 5806 §4: who the call was diverted from, and why |
| `History-Info` | `caller.history` | RFC 7044 §9: index, `rc`/`mp`/`np`, RFC 4458's `cause`, the `Reason` escaped into the URI |
| `Answer-Mode`, `Priv-Answer-Mode` | `answering.answer_mode`, `priv_answer_mode` | RFC 5373 §3, with `;require` |
| `Answer-Mode: Auto`, `answer-after=` on `Call-Info` or `Alert-Info`, `info=alert-autoanswer;delay=` | `answering.answer_after` | the standard one and the two conventions phones built before it |
| `Alert-Info` | `answering.alert_info`, `alert_names`, `source` | RFC 3261 §20.4; RFC 7462's `urn:alert:source:internal`/`external`, or `info=alert-internal`/`external` |

**The trust gate.** RFC 3325 §8: a UAS that receives a message "from a previous
element that it does not trust ... MUST NOT use the P-Asserted-Identity header
field in any way". An account names the peers it trusts, by address
(`Account::trust`), and an INVITE arriving from any other address is read with
`asserted`, `remote_party` and `verstat` left empty and `caller.trusted` false.
An account that names nobody trusts nobody. `Diversion` and `History-Info` have
no trust model of their own and are read either way.

**Answering by itself is the application's policy.** RFC 5373 §4.2: "the UAS
MUST NOT" answer automatically without a policy of its own, and applies "a
stricter authorization policy" to `Priv-Answer-Mode`. So nothing here answers
anything: the field is typed and handed up, and `answermode` joins the option
tags an INVITE may `Require` without a 420, because the stack reads it. A
policy that declines an `Auto;require` refuses the call with 403, as §4.2 says.

**Placing a call anonymously.** `Account::privacy(Privacy::withheld())` makes
every call the account places anonymous in the RFC 3323 sense: `From` is
`"Anonymous" <sip:anonymous@anonymous.invalid>` (§4.1.1.3), `Privacy` carries
what was asked for, the call names a temporary GRUU where the registrar issued
one, and the account's own identity goes in `P-Asserted-Identity` only toward a
trusted peer — the one that can still bill the call and has to strip the field
before it leaves the trust domain (RFC 3325 §7). Once an account names a trusted
peer, a call toward any other peer carries no `P-Asserted-Identity` or
`P-Preferred-Identity`, whoever wrote it (§6); an account that names none has
made no claim about a trust domain, and the application's own fields go as
written.

**Why a call ended.** `UaEvent::CallEnded::causes` carries the `Reason` values
(RFC 3326) of the BYE or the CANCEL that ended the call, or of the refusal when
a gateway put a Q.850 one there (RFC 6432): one per protocol, in the order
written. A forking proxy cancels every branch that lost with `SIP ;cause=200
;text="Call completed elsewhere"` (§3.1) — `Reason::is_completed_elsewhere` —
and a phone that reads it shows "answered elsewhere" rather than a missed call.
`hangup_for(call, &[Reason])` writes them on the BYE or the CANCEL a hangup
turns into (a CANCEL asked for before any provisional response is held with its
reason, §9.1), and only the Q.850 ones on the refusal of an unanswered call,
since a SIP one would repeat the status. This layer writes one by itself in the
one place it ends a branch it lost: the BYE to a phone that answered after
another branch was kept carries `cause=200`. It never sends a CANCEL for a lost
branch, because a UAC cannot address one: RFC 3261 §9.1 cancels a whole INVITE,
and §16.7 step 10 makes the forking proxy cancel the others.

**Sending a call somewhere else.** `redirect(call, &Redirect)` answers an
incoming call with a 3xx (RFC 3261 §21.3): `Redirect::moved_temporarily()` for
call forwarding, each target in `Contact` with its `q` when given, and with
`.diverted(reason)` a `Diversion` naming the address that was called above the
ones the INVITE carried (RFC 5806), so the phone that finally rings can show
"forwarded from Alice, no answer". A redirect with nowhere to go is refused,
except a 380, whose alternative is its body.

### STIR/SHAKEN: signing what an account places, verifying who calls it

`verstat` above is what a network before this end concluded. Behind the
`stir` feature, on by default, this end checks for itself (`crate::stir`,
over `sipral-stir`).

**Signing.** `Account::stir_signing(StirSigning::new(signer, number))` signs
every call the account places (RFC 8224 §6.1): a full-form PASSporT (RFC 8225)
with the SHAKEN claims of RFC 8588 — `attest` (A unless told otherwise), and
an `origid` the agent draws once for the account when none is named — in an
`Identity` header field, beside the `Date` §6.1 Step 3 has the signer add.
`orig` is the number the account signs as; `dest` is the number the call is
to, canonicalised by §8.3's first step, or its URI when the target is not a
number (§4.1's `dest.uri`), in the canonical form of §8.5: `sip:user@host`
in lower case, the password, port, parameters and headers dropped. `iat` is the agent's own wall clock
(`UserAgent::set_wall_clock`), which is why the form is the full one: §4.1
requires it of a signer that takes `iat` from its own clock. A call placed
before the agent knows the time is refused with `UaError::NoWallClock`, not
sent unsigned. The same two fields go on every INVITE the call sends, a 422's
retry included. They make the INVITE some five hundred octets longer, which
takes most past the 1300 RFC 3261 §18.1.1 allows a datagram: a signing
account's calls belong on TCP or TLS.

**Verifying.** `UserAgent::set_stir(StirConfig::new(anchors))` gives the
agent the trust anchors — the STI-PA's roots, in a SHAKEN deployment — and
every account's `StirVerification` decides what happens to an INVITE for it:

| `StirVerification` | Verified | A call that does not verify |
|---|---|---|
| `Off` | nothing | delivered, with no verdict |
| `Report` — **the default** | once the agent has anchors; with none, nothing | delivered, the verdict riding on it |
| `Strict` | always; with no anchors nothing verifies | refused with RFC 8224 §6.2.2's response |

An INVITE whose account verifies is held back from the application until its
verdict is in. The first `Identity` header field that can be started on is
verified; one naming a `ppt` this end does not support is ignored (§6.2 Step
1), and a request with none, or only those, has nothing to verify
(`VerificationOutcome::Absent`). The certificate is the application's to
fetch — its cache, its HTTP client, its timeouts — so a PASSporT that needs
one raises `UaEvent::CertificateWanted` with the URL, and the call waits for
`UserAgent::stir_certificate(call, Some(chain))`, or `None` for one that could
not be had, or for `StirConfig::certificate_wait` (four seconds by default),
after which the certificate counts as unavailable. Nothing is sent meanwhile:
the caller has had its 100 Trying, and the phone rings only once it is known
who is ringing it. `answer` and `ring` refuse a call still waiting; `reject`
and a hangup do not, and a caller that gives up ends it as any CANCEL does.

What the crate below leaves to its caller is done here: the calling number
the request names — the asserted identity from a trusted peer, otherwise
`From` — must be the PASSporT's `orig`, and its `dest` must name the called
party (§6.2 Step 2, §6.2.4, which forbids trusting `orig` over the signalling).
The called party is compared in every case: the number in `To` or in the
Request-URI against `dest.tn` (a `tel:` URI, or a SIP URI's user part that
is a number, `user=phone` or not), and a SIP URI against `dest.uri`, both
sides in the canonical form of §8.5, so a PASSporT signed for
`sip:alice@example.com` does not vouch for a request to anyone else. Either
mismatch is `VerificationFailure::OrigMismatch` or `DestMismatch`, 438, and
the verdict's `detail` names what was signed and what the request names.

Every number, the ones a call is signed for as well as the ones a request
is checked against, is read in §8.3's canonical form. Its first step —
the visual separators and a leading `+` dropped — is always taken; the
second, a national or dialled number put in international form, needs the
deployment's dialling plan, which the application gives once to the agent
(`UserAgent::set_number_plan(Some(NumberPlan::new(f)))`): `f` is handed a
number written without `+`, its separators gone, and gives back its
international form, or `None` to keep it as written, which §8.3 allows. A
number written with `+` is never handed to it. Signer and verifier have to
convert alike, or the number one signs is not the number the other checks.

A PASSporT found valid is remembered (RFC 8224 §12.1): the same one in
another request inside its freshness window is refused as a replay,
`VerificationFailure::Stale` with a `detail` that says it was already
verified, and a `Strict` account answers it 403 "Stale Date". The agent
remembers 1024 unless `StirConfig::remember` says otherwise, each until its
`iat` leaves the window, the oldest giving way when it is full; only a
PASSporT whose signature verified is remembered, so only a signer the
anchors trust can fill it. A new `StirConfig` with the same figure keeps
what is remembered; another figure starts again.

A replay is a PASSporT in another request, not the same request reaching
another line. A proxy that forks one INVITE to several contacts sends each
branch the same `Identity`, and two of them can be two accounts of one agent
— two lines, the members of a ring group — so what is remembered is the
PASSporT together with the request it came in (its `Call-ID`, `From` tag
and `CSeq` number, which every branch of a fork shares and a new request
does not, RFC 3261 §8.2.2.2) and the account it reached (`Pending::verify_arrival`,
`sipral_stir::Arrival`). The same PASSporT in the same request on another
account verifies; in another request, on any account, or in the same request
again on an account that already took it, it is a replay. The STIR check is
not the only one a second branch meets, though: while the core still keeps
the first branch's request for §8.2.2.2 — until that INVITE server
transaction ends, over UDP 5 seconds (T4) after the ACK of its final
response, or 32 seconds (Timer H) without one — a branch of the same request
on another line is answered 482 before it is verified at all. Two lines
ringing at once therefore still take one branch, and a ring group that hunts
to the next line right after a CANCEL or a busy over UDP meets the 482 too.
What this lets through is a branch that arrives after the first one's
transaction is gone: right after it over TCP or TLS, more than five seconds
later over UDP, inside the freshness window.

A certificate has authority over the numbers and ranges its TNAuthList names
(RFC 8226 §9). One that names a service provider code instead — what a SHAKEN
certificate carries — covers no number unless
`StirConfig::accept_service_provider_codes(true)` says so: taking a code as
covering every number is a decision about the providers the anchors certify,
and only the deployment that chose the anchors can make it.

The verdict is `UaEvent::CallerVerified`, queued immediately before the
`IncomingCall` naming the same call, and `CallerIdentity::verification` on the
identity that event and `call_identity(call)` carry: the outcome, the
attestation and `origid` of a valid SHAKEN PASSporT, the number it was signed
for and the certificate's URL, or why it did not hold with the response
§6.2.2 prescribes for that (403 "Stale Date", 428, 436, 437, 438) and the
`verstat` it comes to. A `Strict` account sends that response, sets
`verification.refused`, and the call ends there: `CallerVerified`, then
`CallEnded`. The log names the verdict and never the numbers.

## Screening a call nobody asked for

A phone reachable from the internet is dialled by machines that are not calling
anybody, at the hours when nobody wants to be woken. Before an INVITE becomes
any of the above it goes down a ladder, and each rung can end it without the
one below ever running.

**The rate limit.** A token bucket per source address: a burst may arrive at
once, and one more call is earned every interval after that. It is per address
rather than per address and port, because changing a port costs a sender
nothing while the address is what they must own to hear an answer. The default
is deliberately loose — ten, then one every two seconds — because in most
deployments every legitimate call arrives from the one address the phone
registered with, and a limit tuned to a scanner is a limit on your own
switchboard; `limit_invites` is where a deployment says what its own traffic
looks like, and `invite_limit` reads back what took effect. `Rate::new` refuses
a burst of zero and an interval of zero rather than reading them as one and as
"no limit": both are arithmetically meaningful and neither is what the
deployment that wrote them meant, and a setting whose effective value is not
the value that was given is the failure B2 exists to prevent. A deployment that
genuinely wants no floor says `Rate::unlimited`. The table of sources is a
fixed sixty-four entries, because a table
keyed by whatever address arrives is itself the attack. A seat is reused when
its source has been quiet long enough to have earned its whole allowance back,
since such an entry says nothing a new one does not. When every seat belongs to
a source that is still spending — a flood from many addresses — a stranger is
refused rather than admitted untracked: what cannot be limited is not let in,
and a quiet phone is the better failure at three in the morning.

**The policy hook.** `screen` takes anything implementing `Screen`, a closure
included, and it is asked about every INVITE that survives the rate limit. It
gets what a decision needs and nothing more: the address the bytes came from —
not what the `Via` claims, which is whatever the sender typed — and the request
whole. It answers `Take` or `Refuse` with a status of its choosing. It runs
before ringing, before the `IncomingCall` event, before a `CallHandle` exists
and before one map has an entry, which is the point: a hook consulted after any
of that has happened is a notification, not a policy. The rate limit is asked
first because it is two numbers and a short scan where the hook is arbitrary
application code, and code invoked once per INVITE by whoever is sending them
is the second attack.

`Screen` has a second method, `on_replaces`, asked only of an INVITE that
names one of this end's live calls — see **Transfer** below, where the rule it
defaults to is written out. It is defaulted precisely so that everything in
the paragraph above stays true of a policy that only implements `on_invite`,
which a closure is.

**What a refusal looks like.** 480 Temporarily Unavailable from every rung
this stack decides by itself — the rate limit and the full table both — which
is §21.4.18's callee "in a state that precludes communication": exactly what a
screened number is, and also what a phone that is simply switched off says.
One answer for every reason it decided by itself means a scanner cannot tell a
guarded number from an unattended one. The alternatives were read and
rejected: 404 claims definitive knowledge that the
user does not exist and, sent for some numbers and not others, is an oracle for
finding the ones that do; 503 makes a proxy stop sending to this phone
altogether (§21.5.4), so a rate limit answering it would take the extension off
the air, which is what the scanner wanted; 603 and the rest of 6xx claim to
speak for a user rather than for one device (§21.6), so a refusal here would
silence the desk phone the same person is registered on. No `Retry-After`
rides along, although §21.4.18 allows one: it tells a scanner when to come back
and tells a real caller nothing they would act on. The INVITE is answered
rather than dropped, even though silence would say less, because an INVITE
nobody answers is retransmitted for thirty-two seconds and holds a server
transaction here for all of it.

**The policy's own refusal is the policy's own status**, and that is
deliberate: `Screening::Refuse` carries a `StatusCode` because an application
that knows *why* it is refusing may have a better answer than this stack's —
486 for a line its own user is already on, 603 for a number that person has
told it to reject outright. The reasoning above is then advice rather than
enforcement, and it is worth taking: a policy that refuses some numbers with
404 and lets others ring has built the oracle this stack refuses to build.
`on_replaces` is the one place the default is not 480 — it is 403, because an
INVITE naming one of this end's calls in a `Replaces` it has no standing to
take is not a call this end is unavailable for, it is one it will not perform
(§21.4.4). Every one of those refusals, whichever status it named, is counted
the same way and raises no event.

**What a refusal leaves.** Nothing, except four counters. `refusals` reports
how many INVITEs the policy turned away, how many one source calling too fast
did, how many arrived when every seat in the table was taken, and how many were
refused 403 for naming one of this end's live calls in a `Replaces` they had no
standing to take, cumulative since the agent was made, the same way the core
counts what it refuses for want of room. The middle two are one refusal from
the far end and are counted apart because they are two different things to do
about it: one source over its allowance is `limit_invites` set too tight, while
many addresses at once is a flood that wants a firewall. There is deliberately
no event: an event queue anybody on the internet can fill is the same attack
one layer up, and "how often has this happened" is the question an operator
actually has.

Two edges worth knowing. An INVITE arriving on a byte stream has no address on
it, so the source is the far end the application named when it said the
connection was open; a stream bound without one leaves `source` empty, and a
policy that cannot identify a caller may refuse it. The rate limit still
counts such a stream, by the connection itself: every INVITE on it spends from
one bucket, another connection is another caller, and a connection that closes
takes its bucket with it. And an attended transfer completing directly from
the transferee is an ordinary incoming INVITE here, so
a policy that refuses everything it does not recognise will refuse that too —
and if it carries a `Replaces`, `Screen::on_replaces` under **Transfer** below
is the second question it is asked, and the one that decides whether a call is
handed over.

## Session timers

A dialog can outlive the call it describes: a phone loses power, a NAT drops
the binding, a proxy restarts, and the BYE never arrives. Both ends then keep a
session nobody is in — a line billed for nothing on a carrier, an extension
that stays busy on a PBX. RFC 4028 answers it by making the session expire
unless somebody keeps saying it is there, and without it half the deployments
drop calls after a fixed interval and nobody can explain why.

`Supported: timer` goes on every request, whether or not this end wants one,
because that is what tells the far end it may ask (§7.1). An account asks for
thirty minutes by default, which is §4's recommended value, and
`Account::session_interval` turns that down or off. The refresher parameter is
left out of the first INVITE so the negotiation settles it, and carried on
everything inside the dialog afterwards.

The two ends do different things with the same number. The refresher sends at
half the interval (§7.2), which leaves a whole second attempt before anything
expires; the other end waits, and hangs up shortly before expiry — §10's
"minimum of 32 seconds and one third of the session interval" — reporting
`CallEndReason::Expired`. The refresh itself is an UPDATE with no offer where
the peer takes one, and a re-INVITE where it does not; and then the offer is
the one already agreed, byte for byte, because §7.4 wants it to say it has not
changed and RFC 3264 §8 says an unchanged `o=` version is how that is said.

Answering a call, this end settles it: it honours a refresher the caller asked
for, and otherwise takes the work itself, because the end that refreshes needs
a timer that runs. A 422 is not a call that failed — it is an interval that was
too short, so the INVITE goes again on the same `Call-ID` with the number moved
on and the floor the far end demanded (§7.3), once. A second 422 is the far end
contradicting itself. In the other direction, an INVITE asking for less than
the ninety seconds §5 fixes is answered 422 with that floor before the
application ever sees it: there is no policy in it.

## DTMF

DTMF leaves as an RFC 4733 telephone-event when the far end negotiated the
payload and as an in-band tone when it did not; `UserAgent::send_dtmf_info`
sends it over signalling instead, as a SIP INFO (RFC 6086) in either
of two content types, chosen per send because which one a peer takes is a
fact about the peer rather than about this end. Neither has an RFC of its
own: `application/dtmf-relay` comes from an Internet-Draft that expired years
ago and is two lines, `Signal=<key>` and `Duration=<ms>`; `application/dtmf`
is a plain convention, `Content-Type: application/dtmf` and a body that is
the character and nothing else. `interop/harness`'s own `Flow::DtmfInfo`
sends the relay form to the lab's own Asterisk and reads the dialplan's echo
back in whichever of the two that sends; no lab flow sends the plain form.
`Flow::Dtmf4733` and `Flow::DtmfInfo` have since both been run against the
real container (`docs/11-testing.md`), and both pass against Asterisk. The
RFC 4733 form does not yet pass through the lab's Kamailio proxy to
FreeSWITCH — FreeSWITCH's own echo extension there never names the digit
back — so that path stays excluded until the reason is found, rather than
reported passing on Asterisk's word alone.

`send_dtmf_info` takes a whole string rather than one key, and checks it as a
whole before anything goes out: one character no keypad has, anywhere in the
string, refuses the call and sends nothing, not even the keys ahead of it.
What crosses the wire is still one INFO per digit, but not all
at once: over UDP, overlapping non-INVITE transactions can arrive in any
order, so the string is sent one digit at a time, each one only after the
one ahead of it has a final answer. A 2xx sends the next; a refusal, a
timeout or a transport failure ends the sequence there instead, and the
digits still waiting are discarded rather than sent out of order. A string
handed over while a digit of the same call is still unanswered — a keypad
handing over one key per press — goes behind the digits already waiting,
each key keeping its own form and length, instead of going out at once. Each
INFO's own answer arrives as `UaEvent::DtmfSent`, carrying the digit and
whatever status came back — a 415 from a switch that does not read this
`Content-Type` included, so the application learns which of the two forms to
try next without guessing from silence, and for a digit lost mid-sequence
this event, naming that digit, is the only place it is said. An INFO that
gets no answer at all is reported as RFC 3261 §8.1.3.1 says to treat one,
408 when it timed out and 503 when its transport failed, and one challenged
on an account with nothing to answer the challenge with as that 401 or 407.
The same 503 covers the one case that is not an answer to anything: a queued
digit whose own INFO `request_in_dialog` refuses to send once the digit ahead
of it is answered, reported and discarded exactly as any other failure
mid-sequence would be. A length of zero asks for the hundred
milliseconds every one of the three forms of DTMF — RTP, the two INFO bodies
and the C ABI's `duration_ms` — falls back to when the application does not
name one, all reading the one constant, `sipral_ua::dtmf::DEFAULT_DTMF_MS`.
A call holds at most `sipral_ua::dtmf`'s own sixty-four digits
at once, counting the one in flight with the ones waiting behind it; a string
that would carry a call past that many is refused whole, before anything of it
is sent, the same way one with a character no keypad has already was.

Receiving takes both forms too, and reports one digit regardless of which:
an INFO in either content type arrives from `sipral-ua` as
`UaEvent::DtmfReceived { call, digit, held_ms }`, and the facade folds it
together with RFC 4733 digits into one `MediaEvent::DigitReceived`
(`docs/05-media.md`). Only an INFO whose `Content-Type`
is `application/dtmf-relay` or `application/dtmf` is read as a digit: RFC
6086 does not reserve INFO for DTMF, so every other one — RFC 5168's media
control body, a vendor Info-Package, one with no body at all — is answered by
RFC 6086 §4.2.2 instead, with nothing reported: 469 with an empty
`Recv-Info` when it names an `Info-Package`, 415 with `Accept:
application/dtmf-relay, application/dtmf` for a body this stack cannot read
that its sender did not mark optional, and 200 for one with no body. Left
unanswered, it was retransmitted for thirty-two seconds, and RFC 3261
§12.2.1.2 then has the far end end the call; the C ABI counts such an event
and has no way to answer it. A Rust application that does answer them —
media control for a video stream of its own, say — calls
`UserAgent::hand_over_info(true)` and receives each one as
`UaEvent::Unclaimed`, unanswered, for `UserAgent::endpoint` to answer. Of the
two content types this stack
does read, one whose body names no digit, names two, runs past 256 octets
that no one digit needs, or carries a `Duration=` above the ten seconds no
key is held that long, is answered 400 (§21.4.1), and nothing is reported
for it. A
`Duration=` a peer sent is reported exactly as sent rather than checked
against the forty-millisecond floor sending refuses below: that floor is
about generating a tone equipment can recognise, and a peer reporting how
long it already held a key needs none of its own, so `Duration=0` is
reported as `held_ms: Some(0)`, not the hundred-millisecond default sending
falls back to on the same zero. The sixteen characters a
keypad has are one validation, `sipral_ua::dtmf::digit`, that RFC 4733
sending, INFO sending and INFO receiving all read through alike; the
duration bound is not, because sending is generating a tone and receiving is
only reporting one already generated.

## Hold, resume, and the offers that follow

Hold is not a SIP feature. It is the session description already negotiated,
with its direction attributes changed — RFC 3264 §8.4: a stream that was
`sendrecv` becomes `sendonly`, one that was `recvonly` becomes `inactive` —
and the `o=` version moved on. The stack writes that description rather than
asking for it, which is the point: the application says hold, not
`a=sendonly`. Resume puts back the direction each stream started with, which is
not always `sendrecv`; a stream offered `recvonly` is resumed to `recvonly`.

The whole of it, from the application's side — `crates/sipral/examples/register-and-call.rs`
with `--hold`:

```rust
endpoint.agent.hold(call, now)?;
// ... a pause, then ...
endpoint.agent.resume(call, now)?;
```

with `UaEvent::SessionChanged { hold, .. }` reporting each one — `println!("{hold}")`
in that same file prints `held here` and then `not held`, `Hold`'s own
`Display` impl (`crates/sipral-ua/src/session.rs`).

Hold is per direction, so `Hold` has two flags. The far end holding us is read
off what it sends — `sendonly` or `inactive`, or the address `0.0.0.0` that
RFC 2543 used and §8.4 still requires every agent to understand — and reported
as `SessionChanged` rather than inferred by the application.

An application that writes its own re-offer with `reoffer` says whether it
holds the call by what it writes, and that is read back: a description that
resumes a held call has resumed it, and `hold_state` says so once it is agreed.
A flag kept from before would leave the next `hold` finding the call held
already and sending nothing. A change that is not about direction at all — a
codec change, chiefly (RFC 3264 §8.3.2) — goes through `change_formats`
instead, which takes the description whole but writes every stream's
direction itself, from which way the call is held, exactly as `hold` and
`resume` do. A held call stays held through it, and the direction this end
last wrote in an *answer* is never copied into an offer, where it would read
as this end holding the far end in return. Nor is the DTLS role: a stream
keyed by a handshake is offered again with `a=setup:actpass`, whichever role
it has (RFC 8842 §5.5), in the hold and the resume this layer writes itself.

Which request carries it is decided by the dialog first and by `Allow` second:

- a confirmed call uses a re-INVITE. RFC 3311 §5.1 says so outright — "although
  UPDATE can be used on confirmed dialogs, it is RECOMMENDED that a re-INVITE
  be used instead" — because an UPDATE has to be answered at once and a session
  change may need a person to approve it;
- before the call is answered there is no choice: §14.1 forbids a second INVITE
  while the first is in progress, so an early session changes by UPDATE, and
  only when the far end listed UPDATE in an `Allow` (RFC 3311 §4). This end
  advertises it on the INVITE, on a provisional carrying a description, and on
  the 2xx, which is what tells the far end an UPDATE is worth sending.

An offer arriving from the far end is answered here when it keeps the streams
and the formats that were negotiated — a hold, a resume, a peer moving its
media address — because the answer is then this end's own ports and formats
with the direction §6.1 leaves. An offer that changes the codecs, adds a stream
or drops one needs a device this layer does not have, so it arrives as
`Reoffer` with the transaction still open, to be answered with
`accept_reoffer` or refused with `reject_reoffer`. So does any offer on a
secure profile, a hold included: its answer needs this end's own SDES key, or
its fingerprint and the DTLS role the call already has, and this layer holds
neither. A re-INVITE nobody answers is retransmitted and then ends the call,
so it is never simply dropped. A body that claims to be a session description
and is not gets a 488 with the `Warning` §14.2 asks for. A body of any other
type is refused 415 before the change is looked at, below, or ignored when its
sender marked it `handling=optional`; it never arrives as `Reoffer`.

The answer `accept_reoffer` sends is the application's, and it is required:
every `Reoffer` carries an offer — a re-INVITE that came without one is
answered with this end's own offer before anything is handed up (§14.1), and
an UPDATE without one only refreshes the target — and RFC 3264 §5 has an offer
answered, so the method takes the description rather than an `Option` of one,
and the C ABI's `sipral_call_accept_session` refuses a null one with
`SIPRAL_STATUS_INVALID_ARGUMENT`, the request still waiting. It goes out with
two things this layer owns. A hold this end asked for is kept: a stream the answer has
listening again is narrowed back to what the hold allows, so a codec change or
a refresh from the far end does not take the call off hold on the wire while
`hold_state` still says it is held. An answer with nothing held here goes out
byte for byte. And a request that refreshed the session timer gets its
`Session-Expires` back (RFC 4028 §9), as every answer this layer writes itself
already did. An answer that does not parse is refused before the request is
touched, so it can still be answered or refused afterwards.

Glare is handled from both sides. A 491 comes back with the wait §14.1 draws —
2.1 to 4 seconds for the end that generated the `Call-ID`, 0 to 2 for the other,
so the two cannot collide twice — and the change goes out again once when it
expires. Once: §14.1 says "attempt the re-INVITE once more", and a second 491
is reported rather than chased. In the other direction, an offer that crosses
one of ours earns a 491 and one that arrives while an earlier offer of theirs
is still unanswered earns a 500 with a drawn `Retry-After`, which is RFC 3311
§5.2 generalised to both requests. "Crosses" means ours is on the wire: §14.2's
491 is for an INVITE "in progress", and one already refused with a 491 is
over. An offer this end put in a 2xx — the answer to a re-INVITE that carried
none — is on the wire too until the ACK brings its answer, so a re-INVITE or
an UPDATE that overtakes that ACK earns the same 491, rather than a second
offer RFC 3264 §4 forbids before the first is answered. The far end's own
retry lands in the wait this end drew — the two ranges exist so that it
does — and it is answered like any other change; refusing it
would leave the far end's change failed for good while ours went through. If
it is still waiting on the application when this end's wait expires, the
retry waits in turn (§14.1 again) and goes after it. Once the far end's change
has been answered, the session the retry was written against has moved. A hold
or a resume is written again from the session as it now stands, one `o=`
version past the answer (RFC 3264 §8), so it keeps the codec the far end just
moved to. A session-timer refresh goes again as a refresh, with its
`Session-Expires`, repeating the session as the wait left it (RFC 4028 §7.4).
A description the application wrote (`reoffer`, `change_formats`) would undo
the far end's change, so it is not sent: `SessionChangeFailed` with no status
reports it, exactly as the same call made while a change runs is refused, and
the application writes it again against the new session. When nothing was
answered in the wait, the retry is the same bytes under the same version.

This end never starts the collision itself. §14.1 forbids a new INVITE "while
another INVITE transaction is in progress in either direction", and RFC 3264
§4 a new offer before the last one is answered — which, for an offer this end
put in a 2xx, is when the ACK arrives. A `hold` or a `resume` asked for in that
window returns `Ok` and waits, and its re-INVITE goes the moment the running
change is over: answered, refused, or given up on after a 491's second
attempt. What waits is a state rather than a press, so a resume asked for
behind a hold that is still on its way goes after it, and a hold asked for
again before then takes that resume back and sends nothing more. Each is
measured against where the call is headed, not where it was last agreed: a
resume measured against the agreed state while the hold is still on its way
would find the call not held, and do nothing. `reoffer` and `change_formats`
do not wait — their description was written against the session as it stood,
which the running change is about to move — and answer
`UaError::ChangeInProgress` instead, before anything is written: an offer
refused here uses up no `o=` version, so the one written again afterwards is
still one past the last one said. A session-timer refresh that falls due
meanwhile waits a quarter of the interval and tries again. A hold or a resume
still waiting when the call ends goes with it, unsent, and `CallEnded` is the
last word on it.

One judgement call, and it is §5.2's: an UPDATE "MUST be responded to promptly",
and a UAS that cannot change the session without prompting the user "SHOULD
reject the request with a 504". An application here is not a person being
prompted — a voice agent answers in microseconds — so an UPDATE this layer
cannot answer itself is handed over rather than refused on its behalf. An
application that does ask a person answers 504 itself.

## OPTIONS

This layer answers an out-of-dialog OPTIONS with 200 itself, with the same
`Allow`, `Accept` and `Supported` an INVITE would get (RFC 3261 §11.2), and
the application never sees it. Asterisk, and PBXs built on it, send one to
every registered contact on a timer and mark a silent contact unreachable,
after which inbound calls are refused without ringing.

## Reliable provisional responses

A 180 that vanishes costs a moment of silence. A 183 that vanishes costs the
offer or the answer it was carrying, and then the call is set up wrong or not
at all — which is why RFC 3262 exists and why carriers turn it on.

When to use it is not a choice §3 leaves open: `Require: 100rel` on the INVITE
makes every non-100 provisional reliable, `Supported: 100rel` makes it allowed,
neither makes it forbidden, and the 100 is never reliable under any of them.
So `ring` sends reliably exactly when the INVITE asked, and the PRACK that
comes back is answered 2xx here rather than being handed up — §3 makes that
answer unconditional once RFC 3261 §8.2 has let the PRACK through. A session
description in it is the answer when the provisional carried this end's offer
(an INVITE that came without one), and is taken as the call's far end. Any
other is a new offer, and §5 puts its answer in the PRACK's 2xx: one that only
holds, resumes or moves the media is answered from this end's own description,
and anything else — another codec, a stream added, any offer on a secure
profile — arrives as `Reoffer`, exactly as a re-INVITE's would, with the PRACK
held open for `accept_reoffer` (whose 2xx carries the answer alone, without
the `Contact` and `Session-Expires` a re-INVITE's gets) or `reject_reoffer`.
An offer that crosses one of this end's own is refused 491, one behind an
earlier offer still with the application 500 with `Retry-After`, and a
description that does not parse 488.

A PRACK refused for any reason — 420 for its `Require`, 415 for its body, 488,
491 or 500 for its offer — has acknowledged nothing: the endpoint's
`refuse_prack` puts the provisional back on the list of unacknowledged ones and
retransmits it again until the INVITE has its final response, a 2xx waiting
behind it stays held, and the PRACK the far end sends again without what was
refused (§8.1.3.5) is matched on the same `RAck` and lets it go. Forgotten
instead, that retry would have been answered 481, which §12.2.1.2 has the far
end take as the end of the dialog.

Two things wait. A reliable provisional that carried a session description
holds the 2xx to the INVITE until it is acknowledged (§5): an application that
answers a call whose early media is still unacknowledged has its 200 kept here
and sent the moment the PRACK arrives, because two unanswered offers on the
wire at once is a session negotiated twice. And in the other direction, an
offer arriving in a reliable provisional — which only happens for a call placed
without one — is reported with `answer_wanted` on `CallProgress` and answered
with `answer_early`, because §5 puts that answer in the PRACK and only the
application has one.

What §8.2 asks of every UAS before it acts on a request is asked here, in
§8.2's order, and none of it reaches the application. A REGISTER is answered
405 with `Allow` (§8.2.1): this agent keeps nobody's bindings, and RFC 4475
§3.3.7 names that answer for an endpoint that is not a registrar. A
Request-URI whose scheme is not `sip`, `sips` or `tel` is answered 416
(§8.2.2.1), because no such address can ever be this agent's. Then `Require`,
below. Then the body: one that is not `application/sdp`, or that carries a
content coding other than `identity`, is answered 415 with `Accept` or
`Accept-Encoding` (§8.2.3), unless its `Content-Disposition` says
`handling=optional` (§20.11), in which case it is ignored. That is asked of
every request whose body this agent reads — the INVITE that opens a call, and
the re-INVITE, UPDATE and PRACK that can carry an offer inside one — and
before anything else acts on it, so a refused re-INVITE refreshes no session
timer. A PRACK refused this way has acknowledged nothing, as above, and a 2xx
its provisional was holding back waits for the PRACK sent again. Last, an
INVITE whose `Accept` rules `application/sdp` out is answered
406, since every 2xx to an INVITE carries a session description (RFC 4475
§3.3.15). Which range of an `Accept` decides is HTTP's rule, which §20.1
keeps: the most specific, with a media-type parameter more specific than none
(`application/sdp;level=1` over `application/sdp`, over `application/*`, over
`*/*`), and a parameter on `application/sdp` read as naming the SDP this agent
writes, since RFC 4566 §8.1 registers the type with none. An INVITE addressed to no account is
still reported, and when the application answers it the `Contact` names the
address and transport it arrived on, there being no configured one to use.

A request outside a dialog that no handler here claims is answered here too,
after every handler has had its turn, and never reaches the application as
`UaEvent::Unclaimed`: the C ABI has no way to answer one, and before this the
peer retransmitted into silence until the endpoint's own 408 thirty-two
seconds later. What this agent takes outside a dialog is INVITE (with its ACK
and CANCEL), OPTIONS, MESSAGE, the NOTIFYs of subscriptions it opened and —
only when the application asked for them — REFERs (**A REFER from outside any
call**, below); the rest is refused by the one rule §8.2.1 leaves no choice
in:

| The request | Answer | Why |
|---|---|---|
| Its `To` carries a tag, whatever the method | 481 | It names a dialog this agent does not have (§12.2.2) |
| BYE, UPDATE, INFO or PRACK with no `To` tag | 481 | Methods this agent implements only inside a dialog, and this one names none (§15.1.2 for BYE); a 405 would list them in its own `Allow` |
| NOTIFY that matches no subscription this agent opened, `To` tag or not | 481 | Answered by the subscription handler before this rule is reached: "if not, it MUST return a 481" (RFC 6665 §4.1.3), whatever the package — see *Subscriptions* below |
| REFER with no `To` tag, while `allow_referrals` is off | 403 | It names no dialog, so 481 would be untrue of it, and this agent does REFER, so 405 would be too: it is understood and refused on policy (§21.4.4) |
| SUBSCRIBE for the `refer` package | 403 | RFC 3515 §2.4.4: "REFER is the only mechanism that can create a subscription to event refer", and one for a subscription that does not exist "MUST be rejected with a 403" |
| SUBSCRIBE for any other package, PUBLISH (and REGISTER, refused first, above) | 405 with `Allow` | Recognised, not supported: this agent is no notifier, no event state compositor and no registrar (§8.2.1, §21.4.6) |
| Any method RFC 3261 and its extensions do not define | 501 | Not recognised (§8.2.1, §21.5.2) |

The `Allow` of a 405 is the list this agent's answer to OPTIONS carries —
`INVITE, ACK, CANCEL, BYE, OPTIONS, UPDATE, PRACK, REFER, NOTIFY, MESSAGE,
INFO` — the
methods it supports (§20.5), none of which is ever answered 405. A Rust
application that wants to act as a notifier or a presence server of its own
no longer sees the SUBSCRIBE or PUBLISH through `UserAgent::endpoint`: nothing
in the facade or the C ABI answered one, and a UAS that leaves them unanswered
is the §8.2.1 violation this closes.

Inside a dialog the same holds, for the same reason and with one more: RFC
3261 §12.2.1.2 has a UAC whose request inside a dialog gets no answer
"terminate the dialog", so a SUBSCRIBE a peer sends in passing, left
unanswered, used to cost the call. What this agent takes inside a dialog is
the re-INVITE, UPDATE, PRACK, BYE, INFO carrying a digit, REFER and the
`refer` package's SUBSCRIBE and NOTIFY, the NOTIFYs of its own subscriptions,
MESSAGE and OPTIONS (answered as outside one, §11.2); the rest is answered by
the usage RFC 5057 §5.3 matches it to:

| The request inside a dialog | Answer | Why |
|---|---|---|
| INFO in a call, not DTMF | 469, 415 or 200 | RFC 6086 §4.2.2, as under *DTMF by INFO* above; handed to a Rust application instead once it calls `hand_over_info(true)` |
| re-INVITE, UPDATE, INFO or PRACK in a dialog that holds no call | 481 | The invite usage they belong to does not exist here, and RFC 5057 §5.1 has a 481 end that usage and nothing more |
| PRACK matching a reliable provisional of a call already gone | 200 | RFC 3262 §3: a matching PRACK "MUST be responded to with a 2xx" |
| REFER in a dialog that holds no call | 403 | A new usage refused on policy, as outside one |
| SUBSCRIBE for any package but `refer`, PUBLISH, REGISTER | 405 with `Allow` | Recognised, not supported; RFC 5057 §5.1 note 3 has a request "not integral to the usage" affect the transaction only |
| Any method RFC 3261 and its extensions do not define | 501 | RFC 5057 §5.3: "Servers will return a failure response (likely a 501)" |

A `Require` naming an extension this agent does not implement is answered 420
with the token in `Unsupported` (§8.2.2.3), before the application sees the
call. The list of what it always implements is short on purpose: `100rel`,
`timer`, `replaces` and `norefersub` (RFC 4488, granted to every REFER this
end takes). `gruu` is not on it unconditionally — it is honoured
only for the account the request is addressed to, and only once that account
has asked its own registrar for GRUUs (RFC 5627 §4.4), because §4.4 is written
from a UA's own use of them and an account that never asked for one has
nothing to be asked back about.

## Transfer

A transfer is three parties and two of them never speak to each other. The
transferor is in a call and asks the other end to call somebody else; the
transferee does, and reports back; the target knows nothing about any of it
unless a `Replaces` tells it which of its own calls is being taken over.

A blind transfer, the plainer of the two, from `crates/sipral/examples/register-and-call.rs`
with `--transfer sip:carol@sip.example.com`:

```rust
endpoint.agent.transfer(call, &Uri::parse_str(target)?, now)?;
```

REFER is not fire and forget. RFC 3515 §2.4.4 makes it open a subscription, and
the transferee has to say what happened: NOTIFYs carrying a `message/sipfrag`
whose first line is a SIP status line — `100` while it is trying and the real
answer when there is one, the last of them marked
`terminated;reason=noresource` (§2.4.7). `transfer` sends the REFER and reports
what comes back as `TransferProgress` and then `TransferDone`. This end does
not hang up until the transfer has succeeded: hanging up when the REFER goes
turns a transfer that failed into a call that vanished. `TransferDone` is
reported for a refusal or a timeout too, with the status the far end gave, or
a synthesized 408 when there was none to give — a subscription that opened is
one that closes, whatever the referred call did.

A call may have one REFER outstanding at a time; a second is refused with
`WrongState` while the first's subscription is still open. That seat is given
back when the subscription is, which is the closing NOTIFY (§2.4.7) — not the
202, which only opens it (§2.4.2) and obliges the far end to report on it. A
NOTIFY marked `terminated` closes it whatever its body says: §2.4.4 lets the
far end end the subscription with its very first NOTIFY, still carrying a 100,
and nothing arrives after that to free the seat later. Every
other way a REFER can end opened no subscription either, so the seat is freed
at once instead of waiting for a NOTIFY that §2.4.2 never obliges anybody to
send: a final non-2xx, a timeout, a transport failure, a challenge this end has
no credentials to answer, and the call itself ending while the REFER is still
outstanding.

The REFER a call sends carries a `Referred-By` of its own (RFC 3892 §2.2),
naming this call's own `From` rather than its `Contact`: the account's address
on a call this end placed, and on one it answered the `To` the INVITE arrived
with, which is the From every request this end sends in that dialog carries
(RFC 3261 §12.1.1) — a line reached through its contact may have been called
on a number or an alias, and the address of record behind it was never shown
to the far end. The URI goes alone, without the display name the far end wrote
beside it. It used to be the
other way round, and since a call's `Contact` can be a GRUU — a temporary one
on an anonymous call (RFC 5627 §3.3) — repeating it there would have handed
the transferee a routable address it had no reason to be given. RFC 3892 §1
only wants the referrer identified, and the identity a call's `From` already
showed the far end discloses nothing new; an anonymous call's `Referred-By` is
exactly as anonymous as its `From` already was.

Blind and attended differ by one URI parameter. A blind transfer sends
`Refer-To: <sip:carol@example.com>`; `transfer_to` sends the other call's
remote target with an escaped `Replaces` naming the dialog it is in, so the
party at its far end replaces the call it already has rather than answering a
second. The escaping is not decoration — an unescaped semicolon would end the
URI header and the `Replaces` would be lost. The target goes in as a
Request-URI (RFC 3261 §19.1.5), without URI headers or `method`: a dialog's
`Contact` may carry neither, and headers left on it would swallow the
`?Replaces=` into their last value.

The attended one needs that other call first, and it is not an ordinary one: it
exists so the transferor can speak to the target before handing the caller over,
and its dialog is what the `Replaces` names. `consult` places it, on the same
account, and while it is up its state is `Consulting`; one call may consult about
one target at a time, and a consultation may not consult in its turn — a chain of
them names no transfer, since the middle leg would be both the call being handed
over and the one it is handed to. Holding the first call meanwhile is the
application's, because it is a session change and this layer makes none
uninvited. `transfer_to`
then refuses anything that is not up — an early dialog is nothing to hand over,
and RFC 3891 §3 has the far end refuse a `Replaces` that names one it did not
originate. Any confirmed call may be named, not only the consultation: the RFC
replaces a dialog, not a role.

A REFER that arrives is the application's: it comes as `TransferRequested` and
is taken with `accept_transfer`, which answers 202, opens the subscription with
a first NOTIFY, and places the call — or refused with `reject_transfer`. Zero or
more than one `Refer-To` is answered 400 without asking (§2.4.2), because there
is nothing to decide about a request that cannot be read. So is one whose target
is not a URI, and one whose `Replaces` unescapes to a control byte: that value is
written onto a header line of the INVITE the transfer places, and RFC 3891 §6.1
gives it no way to hold one.

`accept_transfer` places the call the same way `call` does: an
offer, with none the INVITE carries no offer and the answer travels in the 2xx
instead; a destination other than the account's; which forks to keep; and
header fields of the caller's own. The last three arrive bundled as an
`OutgoingExtras` rather than an `OutgoingCall`, because the one field
`OutgoingCall` cannot go without — a target — is never the caller's to give
here: it comes from the REFER that was accepted, the same as `Replaces` and
`Referred-By`. The header fields are checked before the REFER is touched,
against everything `call` would refuse and against `Replaces` and
`Referred-By` besides, so a refusal leaves the transfer waiting to be taken or
refused, with nothing on the wire.

The INVITE `accept_transfer` places carries the `Referred-By` of the REFER that
asked for it, because RFC 3892 §2.2 makes that a MUST: "A UA accepting a REFER
request (a referee) to a SIP URI ... MUST copy any Referred-By header field".
It is sent because the RFC requires it and because the far end may have a
policy that reads it — not because it means anything here: an *incoming*
`Referred-By` is proof of nothing in this stack, and §3's signed token, which
is the only thing that would make it proof, is not implemented. A REFER
carrying two of them, which §2.1 forbids, has neither copied: which of two to
pass on is not ours to guess, and a second value is how a sender would make one
end read one field while the other acted on the second. The transfer itself is
not refused over it.

**A NOTIFY of the `refer` package is acted on only where this end opened a
subscription.** §2 is "a REFER request implicitly establishes a subscription to
the refer event" and §2.4.4 is "REFER is the only mechanism that can create a
subscription to event refer", so the record is written when the REFER is sent —
not when the 202 arrives, because §2.4.4 warns that a NOTIFY may beat it — and
it is dropped when the REFER is refused (§2.4.2 makes a 2xx the thing that
obliges the far end to create the subscription at all) or when the last NOTIFY
says `terminated` (§2.4.7). A notification that matches none of that is
answered 481 by the subscription machine and acted on by nobody, which is the
answer RFC 6665 §4.1.3 leaves for a notification against nothing. It matters
more than it sounds: without the record, the far end of any established call
could report a transfer this end never asked for, and the last NOTIFY of one
hangs the call up. Where a notification carries the `id` parameter §2.4.6 puts
on it, it names the `CSeq` of one REFER, and one that names a REFER this end
did not send is not this subscription's news either.

The NOTIFYs this end sends for a REFER it accepted carry that same `id`
(§2.4.6), the accepted REFER's own `CSeq` — always, not only from the second
REFER a dialog carries onward, since the section MAYs it for the first too and
carrying it uniformly needs no per-dialog count of how many REFERs have
arrived.

**The subscription a taken REFER opens is a real one**, §2.4.4's "same as a
subscription created with a SUBSCRIBE request". Every `active` NOTIFY says how
long it has left — `active;expires=3600` on the first — because RFC 6665 §4.2.2
makes the parameter compulsory; an hour, because §3.4 wants the duration
"longer than the time the referenced request will be given to complete" and the
INVITE this end places carries no `Expires`, and because the subscription is
over the moment the call has its answer anyway. The far end may refresh it
with a SUBSCRIBE in the same dialog (answered 200, with an `Expires` never
longer than what is left, and a NOTIFY of the whole state at once, §4.2.1.2),
or end it with `Expires: 0` — answered 200, then a last NOTIFY
`terminated;reason=timeout`, and the call it asked for goes on untouched,
because §2.4.4 says ending the subscription "is not an indication that the
referenced request should be withdrawn". A subscription nobody refreshed ends
the same way when its hour is up (RFC 6665 §4.2.1.4). A SUBSCRIBE for `refer`
that names no subscription this end holds is 403 (§2.4.4).

A call that cannot even be sent once the 202 has gone — its account's
transport is gone, say — ends the subscription at once with §2.4.5's own
minimal body for a failed reference, `SIP/2.0 503 Service Unavailable`, rather
than leaving the far end with a 100 nothing follows; `accept_transfer` returns
the error, and a second REFER on the call is not held behind the first.

**`Refer-Sub: false` is granted** (RFC 4488). A REFER carrying it is answered
202 with `Refer-Sub: false` of this end's own, which §4 makes the way to say so,
and then no subscription exists: no NOTIFY is sent, and outside a dialog no
dialog is made. `norefersub` is among the option tags this agent understands,
so a `Require: norefersub` is not a 420.

### A REFER from outside any call

RFC 3515 §4.1's own example REFER has no `To` tag: it names no dialog, and asks
this end to place a call it is not already in. That is click-to-dial — a
switchboard, a CRM or an operator console telling a phone to ring somebody
from its own line — and it is also the most direct way for a stranger to make
a phone dial a premium-rate number. This stack answers challenges and issues
none, so it has no authenticated peer to hold such a request to, and
`Referred-By` is a header field the sender wrote. So:

**Off by default.** `UserAgent::allow_referrals(false)` — the state of a new
agent — refuses every REFER outside a dialog with 403, before anything reads
it. Not 481, which would claim it names a dialog, and not 405, which would
claim this agent does not do REFER; 403 is "understood, and not fulfilled"
(RFC 3261 §21.4.4). A REFER whose `To` does carry a tag still names a dialog
this end lacks, and is 481 either way.

**On, it is the application's decision each time.** With
`allow_referrals(true)`, a REFER outside a dialog first meets the screening an
INVITE meets — the rate limit per source address and the application's
`Screen`, which is handed the REFER as `Incoming::request` and can tell the two
apart by method; a refusal is counted in `refusals()` as the INVITE it would
have become. Then what cannot be acted on is refused without asking: zero or
two `Refer-To` or no `Contact` is 400 (§2.4.2, §2), a target that is not SIP,
SIPS or tel is 403 ("A UA not capable of accessing non-SIP URIs SHOULD NOT
accept REFER requests to them"), a Request-URI and `To` that name no account
here is 404 (§8.2.2.1: there is no line to place the call from), and a
seventeenth one while sixteen are held is 486. What survives is
`UaEvent::ReferralRequested`: the referral's handle, the account it arrived
for, the target, whether its `Refer-To` carried a `Replaces`, its
`Referred-By` and the REFER itself. Nothing is answered on the application's
behalf.

**The referral is a `CallHandle` of its own, not a call.** It is drawn from the
same count every call's handle is, so it never collides with one, and it is
taken and refused with the two methods an in-dialog REFER already is:
`accept_transfer` answers 202 — whose `To` tag makes the dialog of the implicit
subscription (§2.4.4: the NOTIFYs match the REFER "as they would if the REFER
had been a SUBSCRIBE request") and whose `Contact` is the account's — sends
§2.4.5's 100 at once, and places the call from the account the REFER arrived
for, with the REFER's own `Replaces` and `Referred-By` and never the
caller's, exactly as a transfer does; one NOTIFY follows per provisional and
the last is `terminated;reason=noresource` with the final answer, after which
the dialog is closed. `reject_transfer` answers with the application's status.
The choice of a call-kind handle over a new kind is what lets a layer that
places calls with media of its own — `MediaEngine::accept_transfer`, the C
ABI's `sipral_call_accept_transfer` — take a referral with no new path at all;
the cost is that `call_state` knows nothing of it, which is the truth: there is
no call yet.

**Nothing waits past the transaction.** §2.4.2 has the answer go "before the
REFER transaction expires". A referral nobody answers for 64·T1 is given up —
the endpoint has answered it 408 by then — and `UaEvent::ReferralLapsed` says
its handle is spent. `referral_waiting` answers whether a handle still names
one that can be taken.

`Replaces` on an incoming INVITE is matched before the application sees the
call, and every way it can fail is a different status code (RFC 3891 §3): two
`Replaces` fields on one request is 400, no match or more than one match is
481, a dialog that has already ended is 603, an `early-only` flag against a
confirmed dialog is 486, and an early dialog this end did not originate is 481.
Only a confirmed dialog, or an early one of our own, is replaced — and then the
new call arrives as an ordinary `IncomingCall`, and answering it hangs up the
one it replaced and reports `CallReplaced`.

**Matching a dialog is not permission to take it.** §3 asks the UA to "verify
that the initiator of the new INVITE is authorized to replace the matched
dialog", and §8 will only have one accepted "if the peer requesting replacement
has been properly authenticated using a standard SIP mechanism". The three
things a `Replaces` names — the `Call-ID` and both tags — travel in every
packet of the call it names, so anyone who watched one packet can write them;
and this stack answers challenges without ever issuing one, so there is no
authenticated peer to compare against. `From` and `Referred-By` are no help
either: they are plain header fields on the INVITE being judged, written by
whoever sent it, and RFC 3892's signed token is not implemented here. So the
comparison is the one thing the sender did not write. **A matched `Replaces` is
honoured only when the INVITE carrying it arrived from the same place the named
call's own signalling does** — the far end itself, or the proxy the line runs
over. Anything else is 403, the matched dialog is left exactly as it was, and
`refusals().by_replaces` counts it.

Three limits, because a security rule that sounds stronger than it is does
more harm than no rule at all. Behind an outbound proxy every inbound INVITE
arrives from that one address, so the check authorises whatever the proxy
relays and the real boundary is the proxy's, not ours. On a datagram transport
the source address is not authenticated either: an attacker who forges it
cannot receive the answer, so cannot take the call over, but can reach the
state arms and get a dialog torn down from a packet it could not have held a
conversation over. And on a byte stream the application bound without naming
its far end there is no source address to record, so a call *received* over
such a transport is measured against nothing and any address-less arrival
matches it, on that connection or another one. A call *placed* is measured
against the address it was placed to, which is written whatever the transport.

The address a call is measured against is recorded once, when the call is
placed or arrives, and not refreshed: a far end that moves fails closed,
refusing a replacement rather than admitting one.

**And the application has the last word: `Screen::on_replaces`.** The rule
above is right as a default and wrong as an absolute. A legitimate attended
transfer whose transferee reaches this end *directly* rather than through the
line's proxy arrives from an address no call here was placed to, and the strict
rule refuses it — that is a deployment, not a corner case. So the rule is a
defaulted hook rather than a wire: `on_replaces` is handed the INVITE and a
`Replacing`, which says which of this end's calls would be hung up
(`Replacing::call`) and whether it came in on that call's own flow
(`Replacing::same_flow`). Its default body is `Replacing::strict`, which is the
paragraph above and nothing else, so a policy that does not override it — every
policy that could have been written before the hook existed, closures included
— behaves exactly as it did, and so does an agent with no policy at all.

An override can widen the rule for the case it recognises and hand everything
else back to `Replacing::strict`, and it can tighten it just as well: refusing
a `Replaces` that *did* arrive on the call's own flow is a decision the hook
returns, which is what a deployment behind a proxy that relays for strangers
wants. What it returns is answered as it stands, and 403 from it counts in
`refusals().by_replaces` exactly as the built-in refusal does. Two things it
does not get to decide: a `Replaces` that matches no call of ours is 481 before
the hook is reached, so guessing identifiers never runs application code, and
the state of the matched call still has the last word afterwards — §3 declines
a dialog that has already ended with 603 however much anybody wants the
takeover.

What a policy has to judge on is thin, and deliberately said so.
`Incoming::source` is the one thing the sender did not write.
`Incoming::referred_by` is the field RFC 3892 §2.2 has a transferee copy from
the REFER that asked for the transfer, so on a real attended transfer it names
the transferor — but it, and `From`, are plain header fields on the INVITE
being judged: whoever wrote one wrote the other, and RFC 3892 §3's signed token
is not implemented here. They are context for recognising a transfer you were
expecting. They are never authority.

## Subscriptions

RFC 6665's event framework, with the lifetime, the refresh, the expiry, the
re-subscription and the termination handled by the stack. `subscribe` takes an
account and a `Subscribe` — a target and an event package token — and gives
back a handle; nothing else is needed for as long as the process runs.

**The dialog is opened by the `NOTIFY`, not by the 200.** §4.4.1 says so in as
many words, and it matters: the route set is taken from the notification, so a
refresh follows the proxies that record-routed *that* rather than the ones on
the answer to the SUBSCRIBE. The consequence is that a subscription is matched
by §4.4.1's three things and nothing else — the `Call-ID`, a `To` tag on the
NOTIFY equal to the `From` tag of the SUBSCRIBE, and a matching `Event` — all
of which are known the instant the SUBSCRIBE is handed to a transport. That is
why the `From` tag is chosen here rather than left to the endpoint to mint, and
why a notification arriving **before** the 200 establishes the subscription
normally. §4.1.2.4 requires that a subscriber be prepared for it, and real
equipment sends it that way.

The dialog carries a sequence number the SUBSCRIBE already used, because the
SUBSCRIBE went out before the dialog existed. Starting the refresh at one again
is a `CSeq` running backwards, which §12.2.2 answers with a 500, and a
subscription that can never be refreshed lapses an hour later for no visible
reason.

**Timer N.** §4.1.2.4 starts it at 64·T1 when a SUBSCRIBE goes and stops it at
the first notification; if it fires there is no subscription and there never
was one, whatever the 200 said. It runs again for every refresh (§4.1.2.2).
Without it, a notifier that accepts and then says nothing leaves a lamp dark
for ever.

**The numbers.** The refresh goes at the same 0.85 of the granted interval a
registration uses, and for the same reason. What the notifier grants wins:
first the `expires` parameter of a `Subscription-State` (§4.1.3 makes it
"the authoritative subscription duration"), then the `Expires` of the 200
(§3.1.1), then what was asked for. Re-subscription after a failure is on
RFC 5626 §4.5's back-off, drawn between half the bound and the bound. Two
reason codes skip the first wait because §4.1.3 says to — `deactivated` and
`timeout` — and only the first time, because a notifier that answers an
immediate retry the same way is a loop.

**What a refusal means depends on which SUBSCRIBE it answered.** For the first,
§4.1.2.1 says no subscription was created; for a refresh, §4.1.2.2 splits the
codes: 404, 405, 410, 416, 480-485, 489, 501 and 604 end the subscription and
everything else leaves it "valid for the duration of the most recently known
`Expires` value" — so one bad refresh does not turn a lamp off, and no event
goes out for it, because nothing the application renders has changed. A 489
says the notifier does not know the package and is not retried.

**A failure is an event and it leaves nothing behind.** The handle is minted
before anything is sent, so a SUBSCRIBE that never reaches a transport — the
interface went, the address no longer resolves — is reported as
`SubscriptionEnded { reason: Unreachable, retry_in: None }` under a name the
application already holds, and the record is removed in the same breath. No
timer is scheduled and no map keeps an entry. The same path runs for a refresh
that cannot be sent and for a scheduled re-subscription that fires while the
network is still down.

**Bulk.** `subscribe_many` exists because a busy lamp field is twenty to forty
subscriptions that all go up when the phone starts. Nothing in the stack waits
for anything, so thirty calls to `subscribe` already put thirty requests in the
transmit queue in one pass; what the batch form adds is that the events are
drained once instead of thirty times, and that a target which cannot be sent to
becomes an event rather than stopping the twenty-nine behind it. There is
nothing else the stack can do about it and it does not pretend otherwise: it
owns no socket, so it cannot pace, and pacing is an application calling this
more than once.

**Forking.** One SUBSCRIBE may be answered by more than one notifier — RFC 4235
§3.9 makes that the normal case for dialog state, one per device the address of
record is registered on. Each notification that arrives on a new `From` tag
while Timer N is still running installs a subscription of its own, with its own
dialog and its own refresh, and arrives as `SubscriptionForked`. After Timer N
has passed, §4.1.2.4 has them refused 481.

**`dialog-info+xml` is read in-tree** and merged into RFC 4235 §4.3's coherent
table: full state replaces it, partial state updates it, a version behind what
is held is discarded, and a version more than one ahead that carried only a
change asks for full state back with a refresh. `dialog_info` gives the table
and `DialogInfoTable::phase` gives §3.7.2's virtual state machine over it,
which is what a lamp renders. The reader refuses rather than works hard: no
document type declaration, so no entity declarations and no expansion to bound;
no CDATA; and the nesting, element count, attribute count and value length are
all bounded before the first byte is read. A document that will not read leaves
the table exactly as it was, because a lamp showing what was last known beats
one showing what a malformed body happened to contain.

**A table nothing is refreshing is not evidence.** `dialog_info` answers
nothing at all unless the subscription is live, and the table is emptied when a
subscription starts, retries or ends — §4.1.2.4's "neutral state", which for
this package is no dialogs. An empty table rendered as a lamp says the
colleague is free, which is the one wrong answer a busy lamp field must never
give, so the application is told it does not know instead. A flow that dies
under a live subscription does the same thing: the refresh is most of an hour
out, and leaving the last thing a working notifier said on screen shows
somebody as free for the rest of that hour.

**Notifications outside a subscription we created are refused.** Unsolicited
`NOTIFY` is a known probe pattern, and §4.1.3 has one answer for it: 481. The
subscription machine gives it, which is why it sits below the transfer handler
in the event chain rather than above it — RFC 3515 §2.4.4 opens a subscription
with a REFER rather than a SUBSCRIBE, so the transfer handler claims the
`refer` package inside a call it is running, and only once everything holding a
subscription of its own has had its turn can anything say that a notification
belongs to nobody. A notification whose `Event` names a package on a dialog
that is ours but did not ask for it gets §4.1.3's other answer, 489.

This is the whole of the decision for `message-summary` too, and it is a
deliberate one: several PBXs, Asterisk among them, send a `message-summary`
`NOTIFY` to a mailbox's own line without a subscription ever having asked for
it. RFC 3842 gives the framework no exception for that, and RFC 6665 §4.1.3's
"it MUST return a 481" is not conditional on the package — so this stack
answers such a `NOTIFY` 481, the same as any other unsolicited one, and an
application that wants message waiting indication subscribes for it first
(`Subscribe::new(mailbox, "message-summary")`, which the framework already
takes any package by name for). A stack that special-cased `message-summary`
to accept it anyway would be reading a misconfigured notifier as a feature.

**`application/simple-message-summary` is parsed into RFC 3458 §6.2's
per-class counts** (`crates/sipral-ua/src/mwi.rs`): a status line, an optional
`Message-Account`, and zero or more `class: new/old (urgent-new/urgent-old)`
lines, one per message-context-class. `UserAgent::message_summary` gives the
whole document, the same way `dialog_info` does for `dialog-info+xml`, and
answers nothing while the subscription is not live for the same reason. The
package defines no version and no partial state (§3.5), so unlike the
dialog-info table nothing here is merged: every `NOTIFY` is a full snapshot and
simply replaces what was held. `UaEvent::MessagesWaiting` is raised alongside
it with the `voice-message` class's counts pulled out — the one RFC 3458 §6.2
names for a phone's message-waiting light — and the status line's boolean,
which is the one field every notifier sends even when it has nothing more
detailed to report.

**`application/conference-info+xml` is merged by RFC 4575 §4.6, and the agent
acts on what the merge says.** Every subscription to the `conference` package —
`subscribe_conference`, `subscribe_call_conference`, or a plain `Subscribe`
naming it — keeps a `Conference` of its own, started afresh with every attempt
because `version` numbers the documents of one subscription and not of the
next. A document that was merged raises `UaEvent::ConferenceChanged` with
`ConferenceUpdate::Applied`, and `UserAgent::conference` gives the picture
(nothing while the subscription is not live, for the reason `dialog_info`
gives). A late or repeated one says nothing. A partial document whose
predecessor never arrived is not merged: the agent refreshes the subscription
by itself, since §4.6 has a gap answered with full state and RFC 6665 §4.2.1
makes the NOTIFY after a refresh carry it, and the picture stands as it was
until that arrives. A `conference-info` marked `deleted` raises
`ConferenceUpdate::Ended`, empties the picture, and gives the subscription up
with an `Expires: 0`, which §4.6 asks of the subscriber.

**`application/pidf+xml` is read for a `presence` subscription** (RFC 3856
§6.8), with the RPID activities of RFC 4480 phones show. Every notification of
the package carries the presentity's whole state, so nothing is merged: the
last readable document is the picture (`UserAgent::presence`), each one raises
`UaEvent::PresenceChanged` carrying it, and one that will not read leaves the
last good one standing. `Subscribe::new(uri, PRESENCE_EVENT)` asks for it.

## Publishing event state

RFC 3903's PUBLISH, for the account's own state at a compositor.
`UserAgent::publish(account, &Publish::new(package), content_type, body, now)`
publishes any package's state and `publish_presence(account, &presence, now)`
publishes a PIDF document under `Event: presence`, one per account: the first
call creates the publication and every later one modifies it under the same
handle, which is what §4.4 expects of a publisher whose state changed. The
Request-URI and `To` are the account's address of record unless
`Publish::target` names another resource; the request leaves where the
account's other requests do.

Everything after that is the stack's: the refresh at the registration margin
under the entity tag the compositor handed back, a modification
(`republish`) naming it, the fresh initial PUBLISH a 412 asks for, the longer
lifetime a 423 names, and the answer to a challenge. **A 401 or 407 is answered
with the account's credentials and is never news**; one nothing can answer — an
account without credentials, or a retry that could not be sent — is decided at
the end of the drain, as a MESSAGE's is, and becomes a refusal. What happens
arrives as `UaEvent::Publication` carrying a `PublishEvent`: `Published` with
the entity tag, the lifetime and when the refresh goes; `Expired` when a
lifetime ran out with no refresh; `Failed` with the reason and the status; and
`Removed` once `unpublish` took the state away (§4.5, `SIP-If-Match` and
`Expires: 0`). A publication ends only there — a refresh that failed or a
compositor that forgot the state leaves the handle naming the same piece of
state, and the next `republish` starts it afresh. An account that is removed
takes its publications with it, and nothing is sent: the state lapses at the
compositor by itself, and a removal needs credentials that went with the
account.

## Conferences: the focus

RFC 4579's one convention is a feature parameter. **A call whose far end says
`isfocus` in its `Contact` belongs to a conference, and that `Contact` is the
conference's URI** (§4.2). The agent reads it from every message that can set
or move the remote target — the INVITE that arrived, the response to one this
end sent, a re-INVITE or UPDATE the far end sent — and `call_conference` gives
the URI, or nothing for a call to anybody else. `subscribe_call_conference`
subscribes to that conference's package outside the call's dialog, from the
call's own account, as §3.4 asks of a conference-aware user agent; the
subscription outlives the call and is kept like any other.

The other side is this end as a focus: `OutgoingCall::focus` places a call
whose `Contact` carries `isfocus`, and `set_focus` says it (or stops saying it)
on a call already up or not yet answered, from its next request or response
on — which is how a far end already talking to this end learns it, by the
target refresh of the next re-INVITE. The `Contact` is still read fresh for
every request (RFC 5627 §4.4); the feature parameter follows whichever address
it is.

## Recording sessions (SIPREC)

A recording session is a call like any other to a recording server, placed
with `OutgoingCall::recording_session(&metadata)` beside its offer. RFC 7866
§6.1 gives it three marks, and the agent writes all three: `Require: siprec`,
so a server that does not do SIPREC refuses it with a 420 instead of taking it
for a call; `+sip.src` in the `Contact`, on the INVITE and on everything the
dialog sends after it; and a `multipart/mixed` body carrying the offer and the
RFC 7865 metadata with `Content-Disposition: recording-session` (§9.1). The
offer is the caller's — one sendonly stream per recorded stream, each with the
`a=label` the metadata names it by — and `siprec::RecordedCall` builds the
usual metadata. What the session records, how the audio reaches it and when it
ends is the facade's (`docs/05-media.md`, "Recording a call to a recorder").

**New metadata goes in an offer.** `update_recording_metadata` keeps the new
document and re-offers the session as it stands, a re-INVITE (or an UPDATE
before the session is up) whose body is the offer and the metadata again:
§9.1 has a request carrying metadata that names SDP labels also carry "an SDP
offer that defines those labels", so metadata alone in an UPDATE is not an
option. Every later offer the session makes carries the latest document. While
another change is running the call answers `ChangeInProgress`, keeps the
document, and is asked again once that change is reported.

**The other side, the recording server.** `accept_recording_sessions(true)`
makes `siprec` an option tag this agent understands instead of one it refuses
420 (RFC 3261 §8.2.2.3), and reads the offer out of a recording session's
`multipart/mixed` body — the INVITE's and every re-INVITE's — where it would
otherwise refuse the body 415. The session then arrives as an ordinary
`IncomingCall`; `siprec::read_recording_offer` reads its metadata, and §6.2's
other half, `+sip.src` in its `Contact`, is `siprec::contact_has_feature_tag`.
The lab's recording server is this, in the headless agent.

## Instant messages

RFC 3428's MESSAGE, pager-model: no dialog, no session, one request and one
final answer. `UserAgent::message(account, target, content_type, body, now)`
sends one out of dialog and `UserAgent::message_in_call` sends one inside a
call's dialog (§4's MAY — "a UAC MAY associate a MESSAGE request with an
existing dialog"). Both return a handle at once, whether or not the request
reached a transport, and the outcome arrives later as `UaEvent::MessageSent`:
200 when the far end delivered it, 202 when a relay in front of it could only
promise to try, a refusal, or the 408/503 this stack reports for one that got
no answer at all (RFC 3261 §8.1.3.1's reading of a timeout and a dead
transport, the same one an unanswered DTMF INFO gets).

**This stack is a UAS that delivers, never a relay**, so an incoming MESSAGE is
always answered 200 once it is accepted — never 202, which §7 reserves for "a
message relay, storing the message and forwarding it later on". It is answered
immediately, before the application sees it: §7 is explicit that a 200 "does
not necessarily mean the user has read it", so there is no decision to ask the
application for at that moment, the same reasoning the OPTIONS answer (above)
rests on. What the application gets is `UaEvent::MessageReceived`
with the whole request — `account` when the line it arrived on could be told,
`call` when it rode inside a dialog rather than starting fresh.

**`text/plain` is always taken** (§4 makes it mandatory), and anything else is
checked against what the account declared with `Account::accepts_message_type`
— nothing, for an account this agent does not recognise the line of. A body of
a type nobody declared is refused 415 with an `Accept` built from `text/plain`
and whatever the account did declare (§21.4.13), and never reaches the
application; a body over this stack's own 32 KiB policy ceiling is refused 413
before it is read at all — an order of magnitude past anything the pager model
in §2 describes.

**The size ceiling on the way out is §8's, and enforcing it is this stack's
job, not the network's.** "The size of MESSAGE requests outside of a media
session MUST NOT exceed 1300 bytes, unless the UAC has positive knowledge that
the message will not traverse a congestion-unsafe link at any hop." Nothing
here has that knowledge by default, so a body over 1300 bytes is refused with
`UaError::MessageTooLarge` rather than handed to the core to fragment over UDP.
`Account::transport_protocol` is how an application gives the knowledge §8
asks for — a stream transport is not held to the ceiling — and it is
deliberately partial knowledge: it says only that *this* hop will not be the
one that turns a large body into a fragmented datagram, which is not the whole
guarantee §8 wants and is the only piece this stack can ever actually know.

**At most one out-of-dialog MESSAGE per target at a time** (§8's own
congestion-safety measure): a second one to the same URI while the first has
not been answered is refused with `UaError::MessagePending` rather than sent,
and a different target is unaffected. The rule is about a destination, not
about a dialog, so its per-URI form does not apply to `message_in_call` — the
destination is the dialog's own, already settled. But §8's very next sentence
gives an in-dialog MESSAGE a rule of its own: "A UAC SHOULD NOT initiate
overlapping MESSAGE transactions inside a dialog, and MUST NOT do so unless
the route set for that dialog uses a congestion-controlled transport at every
hop." `message_in_call` holds to that MUST NOT: unless
`Account::transport_protocol` says the call's account is on a byte-stream
transport, a second in-dialog MESSAGE on the same call while an earlier one
has not been answered is refused with `UaError::MessagePending` too.

**The REFER subscription stays where it is, for now.** It is the same shape and
it should end up expressed as a special case of this machine, but it is not one
today and half-converting it would be worse than either end state. Three things
differ and each is real: RFC 3515 §2.4.4 opens the subscription with a REFER
rather than a SUBSCRIBE, so there is no SUBSCRIBE to match a notification
against and no `Expires` to refresh; the dialog already exists, because it is
the call's; and this end is the *notifier* for half of it, sending the
`message/sipfrag` progress reports rather than reading them. What would be
shared is the reason codes and the `Subscription-State` reader, which are in
`sipral-core::msg` and available to both — and that is the part worth sharing.
The rest is a rewrite of transfer under a machine that would need a notifier
role first, and it belongs in the change that adds one.

One thing is read and not yet written. `Allow-Events` has a reader in
`sipral-core::msg`, and nothing advertises it: §4.4.4 wants it on every
dialog-creating request and on OPTIONS responses, and this stack is a notifier
for `refer` alone, so the honest version is one change across the INVITE, the
OPTIONS answer and the response to a REFER rather than a third of it.

## Codec policy

Codec choice is not in this crate, because `sipral-ua` carries session
descriptions as bytes. The facade (`sipral::MediaEngine`) builds the offer
from a `CodecCatalog` in preference order, intersects it with the answer, and
reports the result as `MediaEvent::Started { codec, .. }` (`docs/05-media.md`).

## Reference event loop

`sipral-ua` ships an optional loop over `std::net`, behind the `reference-loop`
feature and off by default. It exists so that the first call anyone makes with
Sipral takes twenty lines, and so that the bindings have something to mirror.
Nothing in the library depends on it, and nothing else in the workspace opens a
socket.

Its own surface, read straight from `crates/sipral-ua/src/runtime.rs`:

```rust
pub trait Handler {
    fn on_event(&mut self, agent: &mut UserAgent, event: UaEvent, now: Instant);
    fn on_tick(&mut self, agent: &mut UserAgent, now: Instant) -> Control { /* ... */ }
}

impl Runtime {
    pub fn bind(config: EndpointConfig, seed: [u8; 32], local: SocketAddr) -> io::Result<Self>;
    pub fn run(&mut self, handler: &mut impl Handler) -> io::Result<()>;
}
```

None of the examples this crate ships uses it — each writes the handful of
lines a `Handler` would otherwise wrap, because a call also has media, which
`Runtime` does not carry and `crates/sipral/examples/common/udp_endpoint.rs`
does. `Runtime` is what the bindings mirror instead, for a caller with no
media of its own to join.

`Runtime::bind` takes an address and gives back a `Runtime` that owns a
`UserAgent` (`Runtime::agent()`) over a datagram socket. One thread per socket
does the blocking reads and posts what
it finds to a channel; the loop writes what `poll_transmit` gives, hands every
event to a `Handler`, and waits until either something arrives or
`poll_timeout` comes due. The application implements two methods: `on_event`,
which is given the agent as well so that the answer to a ringing phone is one
line, and `on_tick`, which is where it does what nothing prompted it to do and
where it says when it has had enough.

Two things it answers itself: `ResolveNeeded`, with an A lookup, and
`TransportWanted`, by opening the TCP connection §18.1.1 asks for. It passes
`TransportWanted` up as well as answering it, because the two sizes it carries
are the only place a request that did not fit says so, and an application that
never sees them is the application that spends two days believing
authentication is broken.

The event comes only after the endpoint has written the request compact
(`docs/03-core-signalling.md`, `DatagramLimit::compaction`) and found it still
over the line: an answered INVITE a hundred bytes over 1300 goes over UDP
that way, without waiting for anything. Two things above the endpoint take
more off when that is not enough: one SDES suite instead of two
(`CodecCatalog::with_srtp_suites`), about ninety bytes, and no
`a=rtcp-xr:voip-metrics` (`CodecCatalog::with_voip_metrics(false)`),
twenty-four, at the price of the far end's own measurements in the quality
report. The named events are offered on the clocks of the codecs offered
and no other.

Answering it finishes the job rather than only starting it. A REGISTER that
grew past the datagram limit because credentials were added to it is parked
by this layer, with the challenge still held by the endpoint, and is sent
again the moment a transport is bound. Until then it is not reported as a
failure, which is what it used to be, in the same breath as the request for a
connection nobody had been given time to open.

Waiting is bounded, because a stream is not always coming: a registrar that
listens on UDP alone, a firewall that lets no TCP out, an application that
never answers the event (`crate::oversize`). An answer to a challenge held
back for a stream — a call's INVITE, a REGISTER, a re-INVITE or an UPDATE, a
BYE, a REFER, an INFO, a SUBSCRIBE, a MESSAGE, a PUBLISH — waits `STREAM_WAIT`, ten seconds, or
stops at once when the application says the stream cannot be had
(`UserAgent::stream_unavailable`, which the C ABI reaches when a failure is
told of a transport that is not up). A deployment whose server takes SIP
over UDP alone can set §18.1.1 aside for that moment,
`DatagramLimit::without_stream_bytes` (off by default, a deliberate
deviation): everything held is first sent again, and what fits that size
goes over the datagram whole, each one recorded as `transport.kept.datagram`
with its size and the limit; only what still does not fit carries on below.
A call's INVITE then gets one last try
over the datagram with a smaller offer: each media section keeps one of its
`a=crypto` lines, under its own tag — `AES_CM_128_HMAC_SHA1_80` when it
offered that, SRTP's mandatory-to-implement suite (RFC 3711 §5) and so the
one any far end that takes SDES can answer, and the first line otherwise —
through `Endpoint::reshape_challenged_body`. The strongest suite is not the
one to keep: Asterisk offered `AEAD_AES_256_GCM` alone answers 488, and a
retry with no other way out has to be answerable before it is anything
else. When that fits, the call goes on; when
it does not, the call ends as `CallEndReason::Unreachable` with a 513 (RFC
3261 §21.5.6, Message Too Large, standing for this end's own verdict the way
§8.1.3.1's 408 and 503 do) and a `Reason` whose text names the size and the
limit. A REGISTER fails for good with `RegistrationFailure::Unreachable` and
a 513, since sending it again builds the same retry; a session change fails
with a 513 and the call stays as it was (§14.1); the in-dialog requests
settle as refused with a 513; a MESSAGE is reported sent with a 513 and a PUBLISH
fails as unreachable with a 513, never as the 401 or 407 their credentials did
not get to answer. What this layer holds back by itself is left
waiting when the time runs out — the far end is owed it, and a stream opened
later still delivers it — and dropped only when the application says no
stream is coming, a hangup it had decided on then ending the call here.

What this layer sends inside a dialog by itself is held the same way, by this
layer: the ACK to a 2xx, a PRACK with nothing to answer, a transfer's NOTIFY,
the BYE after a 2xx nobody acknowledged or a session that ran out, a hangup it
decided on, a change offered again after a 491, and a subscription's refresh.
Each goes when a transport is bound, and a call whose ACK is waiting is up in
the meantime. A request already waiting is not queued a second time, and a
NOTIFY about a transfer takes the place of the one still waiting for the same
REFER, since RFC 3515 §2.4.5 makes each one the whole status. What the application asks for inside a dialog — a hangup, a
hold, a transfer, an early answer — is refused back to it with `UaError::Send`
exactly as a first request is, changes nothing, and works once the connection
is open.

Three things it does not do, each for a reason worth stating:

- **NAPTR and SRV.** `std::net` resolves a name to addresses and nothing else,
  so RFC 3263's ordering never happens. A deployment reaching a carrier through
  SRV supplies its own resolver.
- **TLS.** None is linked, and none will be. `TransportProtocol::Tls` describes
  a transport the caller has already secured.
- **Wildcard binding.** A datagram socket cannot say which of several local
  addresses a packet arrived on without `IP_PKTINFO`, which the standard
  library does not expose, and RFC 3581 §4 needs that address to answer from
  the right one. So the loop binds to an address you name. A stack listening on
  every interface writes its own loop, which is a dozen lines over a real
  socket API.
